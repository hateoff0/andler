# ANDLER — план переделки архитектуры

Статус: черновик (не коммитить). Принцип: не заплатки — единая целостная
архитектура, даже если что-то приходится переделывать сильно. Каждый пункт:
проблема (с доказательством), решение, объём, риск.

## Ревизия 2: что изменилось и почему

Правки по итогам архитектурного ревью первого черновика — семь конкретных
проблем, каждая с исправлением ниже (не косметика, а исправление
последовательности/дефолтов/владения состоянием до начала работ, чтобы не
вскрывать их посреди рефактора):

1. **Спайк libguestfs (§6) перенесён из фазы 3 в фазу 0** и отвязан от
   фаз конфига/супервизора, от которых технически не зависит — это
   единственный пункт плана с «средней» вероятностью провала (R1), и он
   решает, живёт ли вся ветка GuestMutator в целевом виде. Раньше три фазы
   работы могли пройти впустую по отношению к этому решению.
2. **Зависимости фаз разделены на «жёсткие» и «порядок одного потока
   работы»** (см. таблицу в конце) — DiskChain (§8) технически зависит
   только от фазы 1, не от GuestMutator, и может вестись параллельно.
3. **Единая модель владения состоянием инстанса** (§2.4) — раньше супервизор
   (FSM) и per-instance op-очередь (дисковые цепочки) были двумя отдельными
   «single-writer»-заявлениями без описания, как они соотносятся друг с
   другом; теперь один актор, два вида работы.
4. **Restore меняет дефолт с «ветка» на «discard» (§8)** — ветвление по
   умолчанию само порождало риск R7 (глубокие цепочки → медленные чтения),
   для которого нужна была отдельная митигация; линейная история — то, что
   ожидает почти любой пользователь VM-снапшотов, ветвление — под явным
   флагом для тех, кому нужно.
5. **Границы крейтов для GuestMutator/DiskChain зафиксированы заранее**
   (§6.1) — раньше «типы в core, реализации в services/backends» не называло
   конкретных крейтов; менять границы после того, как код написан, дорого.
6. **Тёплый guestfs-appliance переведён под супервизорную дисциплину** (§6.2)
   — иначе это второй процесс с теми же рисками (P7-P10: тихая паника,
   поллинг вместо `wait`, fire-and-forget), которые рефактор как раз убирает
   у QEMU-процессов.
7. **Идемпотентность op-очереди получила явный ключ** (§14.1) — «join к
   существующей операции того же kind» было недоопределено (два `snapshot
   create` с разными тегами — один kind или конфликт?).

## Ревизия 3: процесс рефакторинга + пять находок от повторного вычитывания кода

Ревизия 2 поправила порядок и дефолты. Ревизия 3 добавляет две вещи:

**Как проводится сам рефакторинг** — новый раздел перед таблицей фаз:
ветвление, коммиты, требования к комментариям и размеру модулей вынесены в
`AGENTS.md` (он тоже правился в этом заходе — точечно, не переписан: добавлены
ветвление, которого там не было вовсе, обоснованное исключение из политики
комментариев для случаев вида «здесь уже наступали на грабли», порог на размер
модуля). Здесь — только то, что специфично для многофазного рефакторинга
поверх этих постоянных правил.

**Пять находок** — не пересмотр решений ревизии 2, а то, что не было замечено
вовсе, потому что ревизия 1 разбирала код по конкретным жалобам, а не построчно
искала недостающее. Три из пяти — проверены по коду, не предположения:

1. **Рестарт демона сегодня = гарантированная смерть VM, иногда хуже**
   (§2.5) — `kill_on_drop` работает только через `Drop`, `restore()` не
   пытается переподключиться к живому QEMU. Это прямо бьёт по цели «не
   паниковать на рефакторе»: следующие месяцы демон будет перезапускаться
   по многу раз в день.
2. **«Ноль root» не покрывает Bridge-сеть** (§12.J) — `ip link add ... type
   tap` вызывается напрямую, без root вернёт `EPERM`, и это нигде не
   учтено в критериях готовности §18.
3. **Isolated-режим — не «есть», а осознанная нереализованная заглушка**
   (§12.J) — открытые вопросы описывали его как рабочий; это неточность
   плана, не кода (сам код честно возвращает ошибку с объяснением).
4. **Отзывчивость супервизора под длинной операцией** (§2.4) — прямое
   следствие модели «всё через супервизора» из ревизии 2: без явного
   требования легко получить регрессию, где `status`/`cancel` не отвечают,
   пока не закончится текущая операция.
5. **Жизненный цикл SSH-ключа хоста** (§12.B) — «baked host key» был
   упомянут без места хранения, прав доступа и истории ротации.

Плюс два явных архитектурных решения, которые раньше были открытыми
вопросами без ответа: **QEMU — единственный бэкенд на обозримое будущее**
(§13.6 — `HypervisorBackend`/`GuestMutator` существуют ради тестируемости,
не ради гипотетического второго гипервизора), и **version-handshake
CLI↔daemon** (§13.19) на время многомесячного рефакторинга, когда версии
расходятся между пересборками.

## Ревизия 4: план не ссылается сам на себя по имени + ещё пять находок

По прямому запросу — этот план временный и будет удалён после рефактора,
поэтому **сам файл никогда не коммитится** (остаётся untracked всю свою
жизнь, удаляется в фазе-последней) и **нигде не упоминается**: ни в
`AGENTS.md`, ни в доках, ни в будущих коммитах и коде — никакой ссылки на
его имя файла, которая после удаления укажет в никуда. `AGENTS.md` уже
говорит о нём только обобщённо («temporary top-level plan file», раздел
Temporary Plan Documents) — эта обобщённая форма обязательна и для любых
будущих упоминаний.
Плюс пять находок от продолжения того же построчного вычитывания кода, что
и в ревизии 3 — первая напрямую выросла из прямого вопроса про `boot_mode`
и `andler connect`.

**Устранение самоссылок (везде, где ревизия 3 их создала):**

1. **`AGENTS.md`, Branching** — пример с именем файла в скобках убран;
   вместо конкретного имени — общее описание паттерна («временный файл
   плана верхнего уровня») и новый подраздел Temporary Plan Documents,
   формализующий правило для любого будущего плана, не только текущего.
2. **`AGENTS.md`, карта документов** — строка про этот план убрана: таблица
   документов — про постоянные документы, план в неё не принадлежал вообще
   (сам факт «зарегистрировать» временный файл в постоянной карте и есть
   источник будущей висячей ссылки).
3. **Commit message-конвенция** — форма «Implements _[имя файла]_ §2.4»
   заменена на `Implements Phase 2 (resolver-access), §2.4` — по номеру и
   слагу фазы, не по имени файла; когда пункт фиксирует постоянный контракт,
   коммит дополнительно указывает итоговый файл (`docs/ARCHITECTURE.md#...`),
   а не этот план.
4. **Критерии завершения (§18)** — было «план пуст или содержит только то,
   что не смёржено»; стало явно: план **удалён**, и `grep` по репозиторию
   подтверждает ноль ссылок на его имя. Пустой файл — тоже висячая ссылка,
   просто с задержкой: кто-то всё равно наткнётся на имя файла в старом
   коммите или доке и откроет пустоту вместо ответа.
5. **Phase-exit чек-лист** — добавлен отдельный пункт 6 специально для
   последней фазы (удаление файла + grep-проверка), отделённый от пункта 5
   (обычное сокращение раздела на каждом phase-exit) — это разные действия
   в разное время, смешивать их в один пункт было неточно.

**Пять находок:**

1. **`andler connect` решает по `kind`, а должен — по эффективному профилю
   `(kind, boot_mode)`** (§12.A, §12.B, P31 в §1). Прямой вопрос, который
   это вскрыл: если у Android-инстанса сменить boot mode на linux, должен
   ли `andler connect` подключаться по ssh? — **да**, но старая матрица
   §12.B не могла даже задать этот вопрос корректно, потому что была ключом
   по `kind` (Linux/Android), а не по тому, что реально загружено в госте.
   Хуже: `current_boot_mode()` сегодня узнаётся только офлайн-mount'ом диска
   (`services/andler-disk/src/boot_mode.rs`) — `instance.toml` о текущем
   boot-mode не знает ничего. Тот же класс проблемы, что и P2 (источник
   правды не там, где его ждёт модель «toml = желаемое состояние»), просто
   для одного поля, а не для конфига целиком — добавлено как **P31**.
   Исправление: `boot_mode` переезжает в конфиг тем же key-path механизмом,
   что и остальные поля (§1); матрица §12.B перестроена на три эффективных
   профиля вместо двух видов гостя; readiness-контракт §A явно ветвится по
   тому же признаку; отдельно зафиксировано, что provision ssh должен
   решаться per-systemd-таргет (`android.target` vs `multi-user.target`),
   а не «на весь образ», раз оба таргета — один rootfs.
2. **TCP-loopback — не граница пользователя, а граница сети** (§12.E,
   §13.16, §L; проверено по коду). Демон слушает `SocketAddr` через
   `ANDLERD_LISTEN_ADDR` (`apps/daemon/src/main.rs`) — обычный TCP-сокет, не
   unix-сокет с правами доступа. `127.0.0.1` защищает от сети, но не от
   другого пользователя того же хоста; §12.E откладывал авторизацию IPC «до
   прослушивания не-127.0.0.1» — но граница пользователя нужна уже сегодня,
   если хост не однопользовательский. Решение поднято до явного выбора, а
   не оставлено подразумеваемым.
3. **«Threat model v2» предполагает v1, которого нет в указанном месте**
   (§L; проверено grep'ом). `docs/ROADMAP.md` ссылается на threat model,
   «documented honestly in `docs/ARCHITECTURE.md`» — там сегодня нет ни
   одного упоминания темы ни в каком регистре. §L переименован из «v2» в
   первое появление раздела, с починкой самой ссылки — тот же класс бага,
   который вся эта ревизия искореняет для себя, но внутри `docs/`.
4. **GuestMutator — первый trait в домене с двумя одновременно живыми
   реальными реализациями** (§6, §9): `QgaMutator`/`GuestfsMutator` обязаны
   давать одинаковый результат на одинаковый вызов, иначе абстракция лжёт
   молча — ни fake-тесты daemon'а, ни integration-тесты одного бэкенда это
   не ловят. Добавлен параметризованный конформанс-набор (фаза 4) и
   постоянный паттерн в `AGENTS.md` (Test Patterns) — понадобится для
   любого будущего trait'а с двумя реализациями, не только для этого случая.
5. **Две вещи закреплены в `AGENTS.md` именно сейчас, а не после того как
   код появится** — обе привязаны к тому, что реально приезжает в ближайших
   фазах: `// SAFETY:`-комментарий формализован как обязательная форма (уже
   так на практике на всех трёх существующих `unsafe`-местах в
   `andler-qemu`) плюс `clippy::undocumented_unsafe_blocks` в
   `[workspace.lints.clippy]`, приуроченное к pidfd (§2.5, фаза 0); и
   обоснование веса новой «тяжёлой» зависимости в коммите, приуроченное к
   статически слинкованному `guestfs-tools` (§6, фаза 4).

## Ревизия 5: код-ревью прогресса по фазе 0 (ветка `refactor/phase0-foundations`)

Первый содержательный чекпойнт после начала реализации — 8 коммитов на ветке
(`033249c`…`4358218`) плюс незакоммиченный diff поверх них. Прогнать
`cargo check` не удалось (в окружении ревью нет rust-тулчейна) — ниже
построчное чтение diff'ов и файлов, не автоматическая проверка; там, где
это важно для доверия к выводу, это отмечено явно.

**Соответствие спеке — сильное, местами буквальное.** `verify_cmdline_marker`
в незакоммиченном `adopt()` использует ровно тот приём, который §2.5 заранее
называл («там уже пишется маркер `-name …,process={instance_name}` … можно
переиспользовать бесплатно») — редкий случай, когда реализация не просто
следует духу плана, а дословно берёт готовое решение оттуда. `supervisor.rs`
(`a667176`) совпадает с §2.4 структурно: один таск владеет FSM/handle/config,
`watch` на чтение, `mpsc`+`oneshot`-ack на запись, персист **до** ack.
`ErrorKind` (`825cb21`) — честный exhaustive match на 33 варианта. unsafe-линт
(`4e410d7`) реализован даже тщательнее, чем предлагала ревизия 4: нашли 11
unsafe-мест по всему репозиторию, а не только 3 в `andler-qemu`, которые
проверял я, — формулировка в `AGENTS.md` была точна для того, что я реально
смотрел, но читалась как утверждение про весь репозиторий; это не проблема
реализации, это неточность моей же формулировки, и хорошо, что её
перепроверили и расширили самостоятельно.

**Главная находка — §2.5 закрывает P8 (смерть процесса не по таймеру), но не
закрывает исходную мотивацию раздела.** Сам §2.5 (ревизия 3) описывал
`kill_on_drop` только в контексте `SIGKILL`/OOM/`abort()` — случаев, где
`Drop` не вызывается вообще, — и не рассматривал отдельно, что происходит
при **чистом** SIGTERM/Ctrl+C, то есть при обычном `systemctl restart
andlerd` или Ctrl+C во время разработки. Это была неточность самого текста
плана, не только реализации: мотивация раздела («демон будет
перезапускаться десятки раз в день») явно про этот сценарий, а не про
крахи, но acceptance criteria были написаны так, будто это одно и то же.

Проверено по коду: `shutdown_signal` (`apps/daemon/src/main.rs`, не тронут
в этой сессии) на каждый SIGTERM/Ctrl+C explicitly вызывает `stop_instance(
id, true)` для всех Running/Paused инстансов **до** того, как процесс
демона успевает завершиться; `kill_on_drop(true)` на `Child`
(`process.rs:69`) по-прежнему взведён для обычного (не adopt) spawn. Значит
только что построенный `adopt()`-путь реально сработает лишь при жёстком
крахе демона (`SIGKILL`/паника/OOM) — то есть не в том сценарии, который
мотивировал раздел с самого начала. Это не баг одного коммита — это то, что
не видно ни в одном diff'е по отдельности, только на трассировке через
`main.rs` + `process.rs` + новый `backend.rs::adopt` вместе.

Добавлено как **R9** (§17) и как явное дополнение к acceptance criteria
§2.5 ниже. Решение — за автором реализации, оба варианта валидны, но один
из двух должен быть принят явно, а не остаться неочевидным следствием того,
что `shutdown_signal` никто не пересматривал в свете `adopt()`:
(a) SIGTERM/Ctrl+C больше не тушит VM — `kill_on_drop` снимается и для
обычного spawn, демон-процесс просто завершается, супервизор-таски уходят
вместе с рантаймом, реальные QEMU-процессы переживают и подхватываются
`adopt()` на следующем старте тем же путём, что и после краха; «выключить
всё по-настоящему» — отдельная явная операция (RPC/флаг), не побочный
эффект SIGTERM; либо
(b) текущее поведение — осознанный дефолт («restart демона всегда мягко
останавливает VM»), тогда `adopt()` целенаправленно только страховка от
краша, и это стоит явно зафиксировать в `docs/ARCHITECTURE.md`, а не
оставлять неочевидным следствием двух не согласованных друг с другом кусков
кода.

**Вторая находка — таск супервизора не наблюдаем при панике.**
`spawn_supervisor` (`supervisor.rs`) делает `tokio::spawn(async move {
supervisor.run().await })` и отбрасывает `JoinHandle`. Если
`InstanceSupervisor::run()` запаникует, вызывающая сторона со временем
получит `InstanceSupervisorGone` (канал закрылся) — это не тихий зависон,
деградация видна вызывающему коду, — но сам факт паники нигде не
залогируется, и восстановления не будет. Показательно, что §2.4 уже
специфицировал `JoinSet` с рестартом-по-backoff для metrics-подзадачи
ВНУТРИ супервизора («owns: metrics-задача (JoinSet, рестарт с backoff)») —
план уже знал нужный паттерн для наблюдаемости дочерних тасков, просто не
распространил его на сам супервизорный таск, которым владеет уже `daemon`,
а не супервизор сам собой. Добавлено как guardrail §13.20.

**Третья находка — два systemd-symlink'а удалены без замены.**
Незакоммиченный diff убирает `multi-user.target.wants/
{andler-display-resolution,qemu-guest-agent}.service` без встречной правки.
Не хватает контекста понять: это часть per-target enablement из находки 1
ревизии 4 (§12.B — «включать sshd только на linux-таргете» тем же
механизмом) или незавершённый кусок, оставленный по пути. См. заметку в
§12.B — перед коммитом стоит явно решить одно из двух, а не оставлять diff,
который сейчас просто отключает оба юнита на всех таргетах.

```

        │  wizard / --file / flags / config set / config edit      │
        │        │  один resolver в andler-core (дефолты+валидация) │
        └────────┼──────────────────────────────────────────────────┘
                 ▼
        ┌──────────────────────── gRPC ────────────────────────────┐
        │  daemon: registry из instance.toml (единственный источник│
        │  конфига), супервизор VM на инстанс, ErrorKind→Status    │
        ├──────────────────────────────────────────────────────────┤
        │  GuestMutator (trait в core) — ВСЕ мутации гостя:        │
        │    online:  QgaMutator   (QMP guest-agent, ноль root)    │
        │    offline: GuestfsMutator (libguestfs appliance, ноль   │
        │              root — без nbd/mount/chroot/helper)         │
        │  сверху: пакетные менеджеры (core), трансляторы,         │
        │          boot-mode, provision-манифесты, resolv/build.prop│
        ├──────────────────────────────────────────────────────────┤
        │  DiskChain (core) — цепочки qcow2-слоёв: снапшоты, клоны, │
        │  базовые образы; снапшоты = внешние overlay-слои         │
        └──────────────────────────────────────────────────────────┘
        store (SQLite) = только метаданные снапшотов; helper+sudoers — удалены
```

**Каталог инстанса (целевой)** — всё, что инстанс есть, лежит в одном месте:

```
~/.andler/instances/<id>/
  instance.toml          # ЕДИНСТВЕННЫЙ источник конфига (schema_version)
  disk.qcow2             # активный (верхний) слой цепочки
  disk.snapshots/        # слои снапшотов: <uuid>.qcow2, backing = родитель
  VARS.fd  console.log  qemu.log
```

Свойства конечного состояния: один источник конфига, один resolver, один слой
мутаций, явная модель дисковых цепочек, **ноль root-привилегий**, ноль
дублирования знаний о госте.

## 2. Runtime daemon: супервизия (переделка)

- **P7. Паника в metrics poller'е убила задачу молча** (наблюдалось вживую).
- **P8. Смерть QEMU — поллингом раз в 30с** вместо `Child::wait`.
- **P9. Health check опрашивает все Running-инстансы каждый цикл.**
- **P10. Фоновые задачи — fire-and-forget `tokio::spawn`.**

Решение: **супервизор VM на инстанс** — одна задача владеет `Child::wait`,
QMP-клиентом и metrics-задачей (`JoinSet` + рестарт с backoff); выход процесса →
немедленный FSM-переход; health check — backstop, не детектор; паника фоновой
задачи = событие супервизора. Объём: andler-qemu (process), daemon (supervisor,
health_ops). Риск: самое рискованное место — делать с сохранением FSM-тестов.

**Улучшение до «чистого» daemon'а (дополняет §2):**

1. **Состояние инстанса живёт В супервизоре** (single-writer), а не в
   глобальном `RwLock<HashMap<...>>`. Реестр daemon'а держит
   `Arc<Supervisor>`; `status`/FSM-переходы идут через супервизор
   (snapshot-канал для чтения). Это убирает глобальный лок и гонки
   «состояние изменилось между read и write»; единственный писатель = сам
   супервизор. FSM-логика остаётся в core (чистая), супервизор её применяет.
2. **Сервисные границы**: `DiskOps` (цепочки) и `GuestMutator` — отдельные
   сервисы со своими типами ошибок, не методы god-объекта `Daemon`;
   `Daemon` — координатор (реестр + супервизоры + шина событий + очередь
   операций).
3. **Тестируемость daemon'а без QEMU**: DiskOps/GuestMutator — trait'ы с
   fake-реализациями (in-memory chain, fake mutator); весь daemon-слой
   (FSM-переходы, очередь операций, конфиг) покрывается юнит-тестами без
   железа; реальные реализации тестируются на уровне интеграционных/e2e.
4. **Единая модель владения состоянием инстанса (закрывает разрыв между §2.1
   и §13.7).** Супервизор — **один актор на инстанс**, который владеет ВСЕМ,
   что относится к этому инстансу, а не только FSM-состоянием:

   ```
   Supervisor (task per instance)
     ├─ owns: FSM state (single-writer, snapshot-канал наружу для чтения)
     ├─ owns: per-instance op-queue (single-writer для дисковых цепочек —
     │        §13.7 реализуется КАК очередь внутри супервизора, а не как
     │        отдельный независимый мьютекс где-то ещё)
     ├─ owns: QMP-клиент + подписка на события (§14)
     └─ owns: metrics-задача (JoinSet, рестарт с backoff)
   ```

   Практическое следствие: RPC-хендлер не трогает `RwLock<HashMap<...>>`
   напрямую и не берёт отдельный op-mutex — он шлёт команду супервизору
   инстанса (mpsc-канал или прямой async-вызов на `Arc<Supervisor>`), и
   именно супервизор решает: применить сейчас, поставить в очередь или
   вернуть `Conflict`. Это устраняет класс гонок «FSM говорит Running, а два
   RPC на цепочку дисков выполняются одновременно, потому что это разные
   мьютексы» — при двух независимых заявлениях о single-writer в первом
   черновике эта гонка была возможна. `Daemon` остаётся координатором
   (реестр `Arc<Supervisor>` + шина событий), а не обладателем состояния.

   **Требование к реализации, не деталь на потом**: супервизор не должен
   быть простым последовательным циклом `while let Some(cmd) = inbox.recv()
   { cmd.await }` — если долгая операция (`snapshot create`, `guestfs`-
   мутация) `await`-ится прямо в теле цикла, `status`/`cancel`, посланные во
   время неё, встанут в очередь за ней и не ответят, пока она не закончится
   — то есть ровно то, ради чего §14 вводит `cancel`, перестанет работать
   именно тогда, когда нужно. Долгая операция запускается супервизором как
   под-задача (`JoinHandle`), а сам цикл продолжает читать `inbox` и
   отвечать на быстрые команды параллельно с ней. Это не отдельная фича — это
   условие, без которого «супервизор владеет всем» из этого пункта на
   практике означает «супервизор блокирует всё».

   **Подтверждено код-ревью фазы 0 (ревизия 5):** оба требования этого
   пункта пока не закрыты в `supervisor.rs` — `apply_transition`
   вызывается напрямую внутри `run()`-цикла (`await` в теле матча, не
   под-задача), значит долгая операция сегодня действительно блокирует
   `status`/другие команды на время своего выполнения; это совпадает с
   собственной пометкой «осталось: отзывчивость под длинной операцией» в
   рабочей копии таблицы фаз — можно доверять этой самооценке. Отдельно от
   неё: `spawn_supervisor` (не `apply_transition`, а сам таск-обёртка)
   создаётся голым `tokio::spawn` с отброшенным `JoinHandle` — паника
   внутри `run()` не логируется и не восстанавливается (guardrail §13.20).
   Та же дисциплина `JoinSet`+backoff, которую этот пункт уже требует для
   metrics-подзадачи, должна применяться и к самому супервизорному таску,
   только уже на уровне `daemon`, который его породил.

### 2.5 Восстановление после рестарта демона (reconnect)

**Сегодня рестарт демона убивает все VM, а иногда — хуже: теряет их
невидимо.** Проверено по коду, не предположение:

- `QemuProcess::spawn` (`backends/andler-qemu/src/process.rs:58`) ставит
  `kill_on_drop(true)` на `tokio::process::Child`. Это работает только через
  обычный `Drop` — при чистом завершении процесса или размотке стека при
  панике. При `SIGKILL`, OOM-killer, `abort()` — `Drop` не вызывается,
  `kill_on_drop` не срабатывает, и QEMU-процесс переживает демон как сирота.
- `Daemon::restore()` при старте безусловно помечает любой Running/Paused/
  Starting/Stopping инстанс как `Error` («backend handle was not
  persisted») и не пытается найти реальный процесс. Если он пережил падение
  демона — демон теперь никогда о нём не узнает: `andler list` покажет
  `Error`, а QEMU-процесс с открытым диском и display провисит в системе до
  ручного `kill`.
- Под systemd (`Restart=on-failure`, `KillMode=mixed`) есть частичная сетка
  — cgroup-cleanup при рестарте, вероятно, подчистит сирот. При прямом
  запуске (`cargo run`/`andlerd` без systemd — то есть именно то, как демон
  будет запускаться десятки раз в день на протяжении этого рефакторинга)
  сетки нет вообще.

**Это не отдельная «фича на будущее» — это прямое условие цели «не
паниковать на этапе рефактора».** Стоит закладывать в супервизора с фазы 0,
а не пристраивать потом:

- QMP-сокет — файл на диске (`qmp_socket_dir().join("{id}.sock")`),
  переживает рестарт демона, потому что QEMU сам держит его как сервер.
  При `restore()`: проверить, отвечает ли сокет на `query-status`; если да
  — восстановить FSM-состояние и `BackendHandle` из ответа вместо
  безусловного `Error`.
- `tokio::process::Child` нельзя «присвоить» существующий PID для `wait()`
  — нужен другой механизм ожидания смерти процесса, который умеет работать
  и с только что заспавненным, и с уже существующим PID. На Linux это
  `pidfd_open` + `AsyncFd`. Это не отдельный механизм ради реконнекта: это
  ровно то же самое, что и так нужно для честной замены поллинга на
  `wait()`-семантику (P8) — если реализовать P8 через pidfd, а не через
  встроенный `Child::wait()`, реконнект после рестарта получается почти
  бесплатно как следствие, а не вторая реализация. `libc = "0.2"` уже есть
  в зависимостях `andler-qemu` — скорее всего, этого достаточно (сырой
  `libc::syscall(SYS_pidfd_open, ...)`, если готовой обёртки нет в
  запиненной версии); точный API — проверить на спайке в фазе 0, не
  утверждать заранее.
- Сетевая информация для Bridge-режима восстанавливается детерминированно
  без дополнительной персистентности — `tap_iface` уже строится как
  `format!("tap{}", cfg.id)` в `cmdline.rs`.
- Верификация «это тот самый процесс, а не переиспользованный PID» — через
  `/proc/<pid>/cmdline`: там уже пишется маркер `-name ...,process=
  {instance_name}` для других целей, можно переиспользовать бесплатно.
- Незавершённая на момент падения операция (например, `snapshot create` в
  процессе) — при реконнекте не домысливается, а помечается как «неизвестный
  результат», с явной подсказкой пользователю проверить состояние (`andler
  snapshot list`) перед следующим действием; авто-докат/авто-повтор здесь
  опаснее, чем честная неопределённость.

Если после спайка фазы 0 выяснится, что pidfd-подход не тянет (например,
целевые дистрибутивы дают более старое ядро, где `pidfd_open` недоступен —
нужен Linux 5.3+) — суженный вариант: демон при рестарте хотя бы **находит**
осиротевшие процессы по qmp-сокету и явно завершает их с логом, вместо того
чтобы молча терять их из виду навсегда. Это не даёт reconnect, но убирает
худший исход (невидимый сирота) даже без него.

**Дополнено по итогам код-ревью фазы 0 (ревизия 5) — acceptance criteria
раздела неполны без этого:**

- `shutdown_signal` (graceful SIGTERM/Ctrl+C) обязан быть согласован с
  `adopt()`, а не оставлен как было: сегодня он explicitly останавливает
  каждый Running/Paused инстанс перед выходом, и `kill_on_drop(true)` на
  обычном (не adopt) spawn всё ещё активен — значит reconnect фактически
  достижим только при `SIGKILL`/OOM/панике, не при обычном рестарте демона,
  который и был исходной мотивацией раздела. Явное решение (R9, §17):
  либо снять `kill_on_drop` и убрать принудительную остановку из
  `shutdown_signal` (graceful signal = демон уходит, VM остаётся, `adopt()`
  подхватывает на следующем старте так же, как после краха — «выключить
  всё по-настоящему» становится отдельной явной операцией), либо явно
  задокументировать «restart демона мягко останавливает VM» как принятый
  дефолт в `docs/ARCHITECTURE.md`, раз `adopt()` тогда только страховка от
  краша.
- Сам этот раздел (в ревизии 3) был неточен в постановке: acceptance
  criteria описывали `kill_on_drop` только для `SIGKILL`/OOM/`abort()` и не
  рассматривали чистый `SIGTERM`/Ctrl+C отдельно, хотя мотивация раздела —
  именно про частый обычный рестарт, а не про крах. Реализация фазы 0
  построена корректно относительно того, что было написано; написано было
  неполно — это на разделе, не на реализации.

**СДЕЛАНО (фаза 0, §2.5 ч.2, ветка `refactor/phase0-foundations`, коммиты
`4358218`…`27c356e`)** — принято решение (b): graceful SIGTERM/Ctrl+C
остаётся «демон уходит, VM мягко останавливается» (зафиксировано в
`docs/ARCHITECTURE.md` как явный дефолт), `adopt()` — страховка от
SIGKILL/OOM/паники. Реализовано: pidfd-ожидание смерти (P8 закрыт, Error
за ~150мс вместо 30с), `QemuProcess::adopt` (pidfd без kill_on_drop),
владелец QMP-сокета через `query-processes` с фолбэком на
`/proc/<pid>/cmdline`-маркер `process=<name>` (Yama ptrace_scope блокирует
fd-скан осиротевшего процесса), `HypervisorBackend::adopt`,
`Daemon::restore`-adopt для Running/Paused, Starting/Stopping → Error
«result unknown» с указанием `andler status`/`andler snapshot list`;
супервизорный watchdog (§13.20), событийная шина (§14-примитивы), лог-стрим
завершается со смертью процесса. Смоук: SIGKILL демона → qemu жив →
рестарт → Running → stop/remove без сирот; e2e `12_process_reconnect`
(14/14) и `11_process_supervision` (17/17) на живом KVM. **Следующий шаг
(dev-режим рестарта: `SIGTERM`/Ctrl+C под opt-in env-флагом уходит в
adopt-путь, VM остаётся жива) запланирован в фазу 1b** — туда, где
появляется первая долгая операция супервизора (`RunOp`) и вместе с ней

до 1b поведение (b) — единственное. Запись в `docs/ROADMAP.md`
(«Dev-mode daemon restart that preserves VMs»). Остаток фазы 0 по
этому разделу: §6-спайк libguestfs не начат (заблокирован отсутствием

## 6. Единый слой мутаций гостя: GuestMutator (новая подсистема)

### Проблемы

- **P20. Нет механизма доставки софта в существующие инстансы** (touch-мост
  прошивался руками; обновления образа не доезжают).
- **P21. Инстанс не помнит, из какого образа сделан** (нет пина/версии).
- **P22. Android-образ — чёрный ящик** (hwc не конвертит pointer→touch,
  `fake_touch` не реализован — только строка реестра; input-путь фиксирован).
- **P23. Офлайн-мутации требуют root**: nbd/mount/chroot через helper и
  sudoers; вдобавок `debugfs`-костыль для build.prop, «chroot-кухня»
  (bind-маунты /dev /proc /sys + resolv-хак + tmpfs /run) ради пакетных
  установок, ручной NbdGuard flock.

### Решение: абстракция + два бэкенда, ноль root

`GuestMutator` (trait в andler-core): read/write_file, mkdir_p, cp_a, mv, rm_rf,
chmod, symlink, run_command(PackageManagerCommand). Реализации:
- **Online — `QgaMutator`**: обёртка над существующим QMP guest-agent.
- **Offline — `GuestfsMutator`**: libguestfs appliance (guestfish/virt-customize,
  статический `guestfs-tools`); appliance сам поднимает unprivileged QEMU, сам
  монтирует, сам держит эксклюзивный доступ (qemu image lock = та же гарантия,
  что у NbdGuard, без своего кода).

| Операция | Было | Стало |
|---|---|---|
| package install/remove | chroot-кухня | `virt-customize --install` (installroot в appliance) |
| translator staging | host cp в overlay через helper | guestfs cp/mv по тем же путям |
| boot-mode switch | chroot-run ln | guestfs symlink |
| resolv.conf / build.prop | guest-write + debugfs | guestfs write_file; вложенный loop-mount `system.img` внутри appliance — debugfs уходит |
| provision-манифесты (§7) | — | тот же GuestMutator |

**Последствия**: `apps/helper`, sudoers, nbd-модуль, `nbd.rs`/`mount.rs`/
chroot-кухня удаляются полностью после миграции — **ноль root у andlerd**.
E2E 07_guest переезжает на guestfish.

**Критичный деталь реализации (иначе медленно)**: файловые операции
выполняются **одной appliance-сессией на пакет операций** (guestfish со
скриптом: staging = 1 запуск, а не 177), а не по одному файлу за сессию.
Сессии: «создать appliance → батч операций → закрыть». Для read-only
диагностики (guest list/boot-mode get) допустим тёплый appliance на daemon
(одна живая сессия, idle-timeout) — снимает бюджет латентности §13.9.

**Спайк (acceptance criteria)**: 1) install/uninstall на apt/dnf/pacman без
chroot-хакерства; 2) staging+boot-mode через guestfish, эксклюзивность лока;
3) вложенный loop-mount system.img; 4) латентность boot-mode (сейчас ~1с);
5) размер/версия guestfs-tools. Если installroot не заведётся — суженный
вариант (пакеты временно на chroot), но за той же абстракцией.

**Спайк — фаза 0, не фаза 3.** Он не зависит технически ни от конфига (§1),
ни от супервизора (§2) — только от того, что `andler-core` уже определяет
trait `GuestMutator`. Прогон спайка параллельно фазам 0-1, до того как в
GuestMutator вложены ещё три фазы работы: если R1 не проходит, суженный
вариант выбирается на входе, а не после того, как архитектура вокруг него
уже построена.

**Конформанс-тесты между бэкендами (находка ревизии 4, не факультатив).**
`GuestMutator` — первый trait в домене с двумя одновременно живыми
реальными реализациями (не fake-против-daemon, а реализация-против-
реализации). `QgaMutator` и `GuestfsMutator` обязаны давать одинаковый
наблюдаемый результат на одинаковый вызов — иначе абстракция лжёт
вызывающему коду молча, и trait становится источником бага, который ни одна
из существующих тестовых стратегий (fake-мутатор в daemon-тестах §2,
integration-тесты одного бэкенда) не ловит. Один параметризованный набор
тест-кейсов (write_file, mkdir_p, run_command, отражение ошибки) гоняется
против обеих реализаций начиная с того момента, когда обе существуют
одновременно (фаза 4). Паттерн зафиксирован как постоянное правило в
`AGENTS.md` (Test Patterns), не только как задача этой фазы — он
понадобится для любого будущего trait'а с двумя реализациями.

### 6.1 Границы крейтов (решить до фазы 1, а не по ходу)

- `GuestMutator` (trait), `PackageManagerCommand`, `AndroidGuestLayout`
  (§13.12) — типы и trait, без I/O: `core/andler-core`.
- `QgaMutator` (обёртка над существующим QMP guest-agent) — `backends/
  andler-qemu`, рядом с `qmp.rs`; она уже там технически живёт, просто нет
  общего интерфейса.
- `GuestfsMutator` (libguestfs appliance) — **новый крейт `services/
  andler-guestfs`**, не расширение `andler-disk`: `andler-disk` сегодня
  отвечает за qcow2/DiskChain (§8), у guestfs-appliance другой жизненный
  цикл (внешний процесс, appliance-boot, батч-сессии) и другой набор
  зависимостей (libguestfs-tools) — смешивать их в один крейт означает тянуть
  guestfs-зависимость в код, которому она не нужна (DiskChain), и наоборот.
- `DiskChain` (реализация, §8) — остаётся в `andler-disk`, он логически
  продолжает существующий qcow2-код этого крейта.
- Оба (`QgaMutator`, `GuestfsMutator`) реализуют один и тот же
  `core::GuestMutator`; `daemon` выбирает реализацию по состоянию инстанса
  (online → Qga, offline → Guestfs), не дублируя эту логику в CLI.

### 6.2 Тёплый appliance — под супервизорной дисциплиной, не отдельный процесс-сирота

Митигация R2 (латентность read-only офлайн-операций) — держать один живой
guestfs-appliance с idle-timeout на daemon. Это **второй тип долгоживущего
внешнего процесса** после QEMU-инстансов, и он обязан жить по тем же
правилам, которые §2 вводит для VM-процессов, иначе рефактор молча
воспроизводит P7-P10 (тихая паника поллера, поллинг вместо `Child::wait`,
fire-and-forget `tokio::spawn`) для appliance:

- appliance-задача — тоже супервизируемая task (`JoinSet`, не голый
  `tokio::spawn`), с owner'ом, который видит её падение как событие, а не
  тишину;
- `Child::wait` на appliance-процесс, а не поллинг;
- idle-timeout убивает appliance явно (kill_on_drop) — appliance не
  переживает graceful shutdown daemon'а (§13.11 расширяется на него же);
- appliance не общий между инстансами одновременно (эксклюзивность — уже
  требование R1/§6, но явно: одна активная appliance-сессия за раз, вторая
  ждёт очереди, не спавнит параллельный процесс).

**СДЕЛАНО (фаза 0, §6, спайк, ветка `refactor/phase0-foundations`)** —
прогнан на живом хосте (libguestfs 1.60.1, supermin 5.3.5, Arch, unprivileged,
KVM via /dev/kvm). Общий вывод: **GuestfsMutator жизнеспособен для файловых
мутаций с ноль root; installroot не заводится — суженный вариант подтверждён
на практике.** Итоги по критериям:

1. **Install/uninstall (installroot) — НЕ заводится**: appliance Arch-хоста не
   содержит ни одного пакетного менеджера (`/usr/lib/guestfs/supermin.d/
   packages`: только `rpm-tools`; apt/dnf/pacman/yum отсутствуют), а
   `virt-customize --install` требует `installroot`-процесс с пакетным
   менеджером внутри appliance (тест: «no operating systems were found»,
   далее не уехал). Сужающий fallback из §6/§12.L: package-операции остаются
   на существующей chroot-кухне (root через helper), GuestfsMutator не
   берёт run_command(PackageManager) — все файловые операции берёт. R1
   подтверждён частично: не спайк-провал, а подтверждённый суженный вариант.
2. **Staging + boot-mode — ок**: guestfish батч (mkdir/cp/write/symlink/
   upload на qcow2) работает без root, эксклюзивность подтверждена: второй
   параллельный клиент на тот же образ падает с ошибкой открытия (qemu
   image lock в appliance) — «та же гарантия, что NbdGuard, без своего
   кода» достигается.
3. **Вложенный loop-mount system.img — сужено до лучшего**: у appliance
   нет `/bin/mount`/`/bin/sh` (вложенный mount невозможен), но `system.img`
   подключается **вторым диском той же appliance-сессии** (`add system.img`,
   `mount /dev/sdb /mnt`) — запись в него прошла. debugfs-костыль уходит,
   loop-mount не нужен вообще.
4. **Латентность — ок**: одна appliance-сессия с записью ≈ 1.7–1.8 с
   (после первого appliance-build; холодный старт ниже ~1.0 с кэшом,
   supermin-сборка кэшируется в `/var/tmp/.guestfs-$(id -u)`). Батч-сессии
   на пакет операций обязательны (не по-файлово); тёплый appliance —
   фаза 4 (§6.2).
5. **Вес/версия — ок**: `guestfs-tools` 29 MiB установленные,
   appliance-кэш ~1 GiB в `/var/tmp` (ждёт пока supermin ребилд под
   библиотеки хоста); но **линковать ничего не нужно** — `GuestfsMutator`
   исполняет `guestfish`/`virt-customize` как внешние бинарности (тот же
   паттерн, что `qemu-img` сегодня), зависимость — runtime-tool, не
   static-линк; `doctor` обязан проверять наличие (план §12.K, задача —
   в этой фазе зафиксирована).

## 8. Диски, снапшоты, клоны: явная модель цепочек (новая подсистема)

### Проблемы текущей схемы

- **P28. Внутренние снапшоты qcow2** (`blockdev-snapshot-internal-sync`):
  снапшот живёт внутри файла диска — файл растёт на весь дельта-объём,
  удаление снапшота **переписывает файл** (`qemu-img snapshot -d`), live-revert
  невозможен (нет vmstate-механизма для блочного отката).
- **P29. Метаданные снапшотов в двух местах**: SQLite-таблица + список в самом
  qcow2 — дрейфуют.
- **P30. Клоны без модели цепочек**: linked/full/shared-base — отношения
  выводятся сканом backing-файлов (`find_live_clones` — эвристика O(инстансы));
  клон от снапшота невозможен; «нельзя удалить источник» — вычисление, а не
  свойство модели.

### Целевая модель: `DiskChain` — цепочка qcow2-слоёв как объект домена

Слой (layer): `{path, backing, kind: BaseImage | InstanceActive | Snapshot |
Clone}`. Цепочка: `base → … → активный слой`; снапшоты и клоны — оверлеи на
замороженных слоях.

**Снапшоты — внешние overlay-слои** (qemu-native дизайн):

| Операция | Было | Стало |
|---|---|---|
| create (live) | internal snapshot в файле диска | `blockdev-snapshot` (external): новый файл `disk.snapshots/<uuid>.qcow2` поверх активного слоя; VM продолжает работать на новом слое. O(1), база не растёт |
| restore | `qemu-img snapshot -a`, VM остановлена | остановить → **discard по умолчанию**: слои новее целевого снапшота (и их метаданные) удаляются, новый активный слой создаётся поверх целевого — линейная история, как ожидает пользователь VM-снапшотов. **Ветвление — под явным флагом** `snapshot restore --branch`: старая голова архивируется как отдельная ветка вместо удаления, снапшоты новее цели не уничтожаются. (Live-revert — отдельный шаг: `block-stream`/swap, не в v1) |
| delete | перезапись файла | `block-commit` слоя в родителя (O(дельта)), файл удаляется; средний слой — последовательный commit; ветки без ссылок — `prune` |
| list | SQLite + qcow2 (два места) | SQLite (метаданные) + цепочка файлов; qcow2-список больше не источник |
| export/копия | convert | `qemu-img convert` головы цепочки (standalone) или оверлей на слой (linked); клон снапшота = оверлей на замороженный слой |

**Важно (осознанное решение, пересмотрено в ревизии 2)**: модель цепочек
технически допускает дерево (qcow2 позволяет несколько детей у одного
backing-слоя) — но **discard выбран дефолтом**, а не ветвление. Причина:
ветвление-по-умолчанию само создаёт риск R7 (глубокие цепочки → медленные
чтения) для фичи, которую, скорее всего, использует меньшинство сценариев
(git-style история снапшотов VM) — и план тут же требует отдельную
митигацию (периодическая консолидация) от риска, который сам же и породил
дефолтом. Discard по умолчанию держит цепочку короткой без дополнительной
дисциплины; кто явно попросил ветвление (`--branch`) — явно принял и цену
(глубина, консолидация). Дерево как структура данных всё равно нужно в
метаданных (§8 DiskChain), потому что `--branch` существует — просто не
используется по умолчанию.

**Клоны** в модели цепочек:
- linked = новый оверлей на замороженный слой источника; источник удаляется
  только если на его слои нет ссылок (проверка — по индексу цепочек из
  instance.toml'ов + метаданных снапшотов, явная, без эвристик).
- full standalone = convert головы.
- shared-base = оверлей на замороженный базовый образ (пин образа §7);
  базовые образы иммутабельны, обновление = новый id образа.
- консолидация цепочек: существующий `disk compact` + `qemu-img rebase`
  (flatten), как отдельная операция.

**Миграция существующих внутренних снапшотов**: остаются читаемыми
(restore через `qemu-img snapshot -a`), новые снапшоты — внешние; конвертация
старых — отдельная явная команда, не автоматом.

Спайк (выполнен, 2026-08): live `blockdev-snapshot` + `block-commit` на реальной
VM (KVM, QEMU 11.0.3, qemu 11: guest init на голых syscalls пишет WRITE-1 →
live snapshot → WRITE-2 → commit → оба маркера в базе). Подтверждённый
протокол (финальная схема фазы 1b, отличается от ранней версии спайка):
- cmdline обязан задавать **явный node-name** (`-blockdev driver=qcow2,node-name=drive-disk0,file=file-disk0,detect-zeroes=on` +
  `-blockdev driver=file,node-name=file-disk0,filename=...,aio=threads,discard=unmap`). `-drive if=none,id=...` даёт
  безымянный BlockBackend и автоимя узла `#blockNNN` — нестабильно для QMP-операций.
- create: **`qemu-img create` (без `-b`!)** → **`qemu-img rebase -u -F qcow2 -b <абс. путь будущего слоя>`** →
  `blockdev-add {driver:qcow2, node-name:snap-<uuid>, file:{driver:file, filename:..., locking:off, aio:threads}, backing:null, discard:unmap, detect-zeroes:on}` →
  `blockdev-snapshot {node:drive-disk0, overlay:snap-<uuid>}`. Ранняя схема `create -b <активный файл>` с последующей
  «переустановкой» backing-пути не работает: `qemu-img create -b <несуществующий путь>` падает
  («Could not open backing image»), а `rebase -u` с несуществующим backing **работает** (rc=0) — поэтому tmp-файл
  рождается пустым, его backing-ссылка сразу указывает на будущий путь слоя, и rename-пара (активный→слой,
  tmp→активный) завершает переключение без переписывания метаданных. `-F qcow2` обязателен (иначе
  «backing format must be specified»). QEMU сам привязывает backing к активному узлу (chain подтверждён
  query-block). `locking:off` на file-драйвере overlay обязателен (иначе OFD-lock конфликт с активным
  файлом при повторном открытии); `backing` ССЫЛКОЙ на активный узел запрещён (node busy), вложенный
  backing — «The overlay already has a backing image».
- commit (delete снапшота, offline): `qemu-img commit <слой>` → `qemu-img rebase -u -F qcow2 -b <parent>` прямых
  детей + активного (если его backing = слой) → `rm`. QMP-вариант `block-commit {job-id, device:<top-node>,
  top-node, base-node, auto-finalize:true, auto-dismiss:false}` реализован и wire-протестирован, но в 1b
  live-commit не используется (offline проще и crash-safe): **auto-dismiss:false** (не true как в раннем
  спайке) держит job в `query-jobs` до `job-dismiss`, и существующий `wait_job_completion` не ловит гонку
  «job исчез».
- данные подтверждены offline: `qemu-img convert -O raw` после commit — WRITE-1 и WRITE-2 оба в disk.qcow2.
- legacy `blockdev-snapshot-sync` тоже работает (QEMU сам создаёт overlay) при именованном BB, но BB
  безымянный — не используем; `blockdev-replace` в QEMU 11.0.3 отсутствует.
- discard-семантика сохранена: `file.discard=unmap` + `qcow2.detect-zeroes=on` идентичны текущему
  `-drive discard=on,detect-zeroes=on`.
- **Атомарность**: rename-пара + метаданные последним шагом. Crash между rename'ами — реконсиляция
  при старте демона промотит tmp-оверлей в активный диск; crash после rename до INSERT — слой получает
  `recovered-<uuid8>` запись; crash mid-restore — активный диск пересоздаётся поверх головы цепочки.

### 9.1 Наблюдаемость и логирование — первоклассный контракт, не факультатив

По прямому запросу — «качественное логирование вообще всего»: это не
дополнение к daemon'у, а часть его контракта, зафиксированная теперь как
guardrail (см. добавленный §13.18), чтобы регресс в логировании ловился
так же, как регресс в id-схеме или тексте ошибок.

- **P27. Нет метрик самого daemon'а** (RPC-латентность/ошибки, состояния,
  рестарты задач, reconnect'ы QMP/guestfs) — только текстовые логи.
- Решение: tracing span на RPC + итоговая строка; счётчики поверх broadcast.

**Дисциплина логирования:**

1. **Сквозная корреляция через один и тот же ID, от CLI до QMP-байта.**
   Каждый RPC-запрос от CLI несёт `request_id` (генерируется клиентом,
   принимается сервером как metadata); daemon порождает `op_id` для любой
   операции дольше одного запроса. Span-дерево: `request_id` → RPC-хендлер
   → (если асинхронная операция) `op_id` супервизора → QMP-команда/
   guestfs-сессия. Из одной строки лога восстанавливается путь «CLI-команда
   пользователя → что именно daemon сделал с QEMU/guestfs» — сейчас это
   восстанавливается по догадке (P7-P10 наблюдались вживую именно из-за
   отсутствия такой трассы).
2. **Формат — структурированный JSON по умолчанию, человекочитаемый как
   опция.** `tracing-subscriber` с JSON-writer в файл/stdout;
   `ANDLERD_LOG_FORMAT=pretty` — для интерактивной отладки в терминале.
   Структурированный формат обязателен, потому что «хорошее логирование»
   бесполезно, если его нельзя грепать по `instance_id`/`op_id` программно
   (в т.ч. самим `andler doctor`/`andler events`).
3. **Уровни — явная таблица**: error = потеря данных/сбой операции; warn =
   ретраи, деградации, медленные ops (>бюджета); info = lifecycle-переходы,
   начало/конец операций; debug = детали мутаций; trace = QMP-байты. В
   `events` (пользовательский канал) попадают только error/info + операции.
4. **Rate-limit для retry-петель**: QMP-reconnect/health-ретраи логируются
   коалесцированно (первый + каждые N-й + итог), иначе сбойный цикл спамит
   журнал и «хорошее логирование» тонет.
5. **Redaction — явный список полей, которые никогда не попадают в лог**:
   содержимое guest-exec (может нести пароли/токены пользователя), baked
   ssh-приватные ключи (публичный — можно), значения env, переданные в
   provision-манифесты. Structured-логирование увеличивает риск случайно
   залогировать сериализованный объект целиком — эта дисциплина нужна
   именно потому, что формат стал JSON, а не текстовой строкой «на глаз».
6. **Три потока не смешиваются**: daemon-лог (tracing, structured), аудит
   (events.jsonl, пользовательский, §14), guest-логи (qemu.log/console.log,
   ротация §F). Метрики — отдельный broadcast. Ни один поток не подменяет
   другой: daemon-лог может быть debug-уровня и огромным, аудит — всегда
   компактный и предназначен для показа пользователю.
7. **daemon-лог доступен через CLI без похода на файловую систему**:
   `andler logs daemon [--follow] [--json] [--since]` — тот же паттерн, что
   `andler events`, поверх того же файла/потока; пользователь не должен
   знать путь `$XDG_STATE_HOME/andler/daemon.log`, чтобы дебажить.
8. **Метрики daemon'а (P27) — конкретный список, не «что-нибудь»**:
   RPC-латентность по методу (p50/p99), счётчик ошибок по `ErrorKind` (§3),
   число активных супервизоров/инстансов, счётчик reconnect QMP/guestfs с
   причиной, длина per-instance op-очереди. Экспорт — минимум `andler doctor
   --metrics` (текстовый снимок), Prometheus-эндпоинт — опционально, не
   блокер фазы.

## 12. Открытые области, которые нужно продумать до/в ходе работ

Эти темы не закрыты §§1-11 и требуют осознанного решения (вписаны в фазы
ниже как подготовительные подзадачи).

### A. Контракт гостя и готовность (UX-боль из сессии)
Сейчас «грузится ли Android» определяется по косвенным признакам (лог + глаза
пользователя). Нужен **явный контракт гостя**: уровни готовности, которые
daemon умеет показывать в `status`:
`serial up → qga up → display applied → guest os up → (android: waydroid ready)`.
Гостевые компоненты образа должны отчитываться (системные юниты + QGA-пробы +
fw_cfg-фаза). Решает класс проблем «долго грузится — что-то не так?».

**Контракт зависит от эффективного профиля, не только от `kind` (находка
ревизии 4).** `AndroidVm`-инстанс, переключённый в Linux boot-mode
(`AndroidBootMode::Linux`, `andler guest boot-mode`), не поднимает waydroid —
финальная стадия готовности для него та же, что у `LinuxVm` (`guest os up`),
а не `waydroid ready`. Эффективный профиль = `(kind, boot_mode)`, а не
`kind` в одиночку; для `LinuxVm` boot_mode не существует по определению —
профиль всегда «linux». См. P31 (§1) и §12.B.

### B. Доступ в гостя: единая команда, четыре уровня, любой тип VM (приоритет ревизии 2)

По прямому запросу — этот раздел спроектирован полнее, чем остальные пункты
§12, и поднят выше в очереди фаз (см. таблицу в конце): «лёгкий доступ к
любой VM любым способом подключения» — не разрозненные команды под разные
сценарии, а один вход с автовыбором лучшего доступного способа.

**Точка входа: `andler connect <id>`.** Не отдельная команда на каждый
способ — единая, которая сама выбирает лучший доступный уровень для
конкретного инстанса и его текущего состояния, и говорит, что выбрала:

```
$ andler connect myvm
→ ssh доступен (host key baked, port-forward настроен) — подключаюсь по ssh
$ andler connect myvm --level console
→ форсирует serial console, даже если ssh доступен (например, ssh не грузится)
$ andler connect myvm
→ [android, waydroid] ssh недоступен для этого профиля — использую adb shell
$ andler connect android-linux-vm
→ [android, boot-mode=linux] waydroid не поднят в этом boot-mode — подключаюсь
  по ssh, как у Linux VM
```

Уровни — от «работает всегда» до «удобнее всего», деградация по порядку,
если верхний недоступен:

1. **`console` — serial, работает всегда.** `-serial unix:/.../console.sock`,
   attach/detach (Ctrl-]), `console.log` остаётся как лог отдельно от
   attach-сессии. Единственный уровень, который не требует ни сети, ни
   гостевого агента, ни рабочего display — базовый уровень и fallback для
   всего остального, включая диагностику «почему не поднимается ssh».
2. **`ssh` — для Linux-гостей.** Авто port-forward (`network.port_forwards`,
   slirp hostfwd / passt) + **baked host key**: публичный ключ хоста
   попадает в образ через provision-манифест (§7), пользователь `user`
   получает рабочий shell (сейчас — `nologin`, это тоже P-пункт: скрытая
   недоступность). `andler connect` сам проверяет/стартует VM, поднимает
   port-forward, вызывает ssh с правильным ключом; scp/rsync поверх этого —
   без дополнительной настройки. Никаких паролей — только ключи.
3. **`adb` — для Android-гостей.** Тот же port-forward механизм
   (`network.port_forwards`), но `adb connect host:port` вместо ssh; сейчас
   `auto_adb` стоит `false` — это ручной шаг, который `andler connect`
   должен делать сам, раз VM — Android. Уровень «удобный интерактивный
   доступ» для Android ролится через adb, не через ssh (в Android его нет
   по определению гостя).
4. **`exec`/`cp` — программный доступ, для скриптов и тестов, не для
   человека.** `andler exec <id> -- <cmd>` через QGA guest-exec;
   `andler cp <id> <local> <guest>` — файловые операции (online — QGA file
   ops, offline — тот же `GuestMutator`, §6, что и все прочие файловые
   мутации — не отдельный путь). Этот уровень работает даже без ssh/adb,
   потому что не зависит от сети гостя вообще.

**Матрица «что доступно для какого эффективного профиля»** (часть §M, но
приоритетна здесь; ключ — `(kind, boot_mode)`, не голый `kind` — находка
ревизии 4, см. §12.A/P31) — явно документируется и проверяется `andler
doctor`, а не выясняется опытным путём:

| Эффективный профиль | console | ssh | adb | exec/cp |
|---|---|---|---|---|
| Linux VM (`kind=LinuxVm`) | да | да (после provision §7) | — | да |
| Android, boot-mode=android (`kind=AndroidVm`, дефолт) | да | — (waydroid-сессия, не Linux-сессия) | да | да |
| Android, boot-mode=linux (`kind=AndroidVm`, после `guest boot-mode set linux`) | да | да (та же provision §7 — см. ниже) | — (waydroid не поднят) | да |

**Provision ssh — по systemd-таргету, не по образу целиком (уточнение
находки ревизии 4).** Один и тот же rootfs грузится и в `android.target`, и
в `multi-user.target` (`boot_mode.rs`) — значит «включать ли sshd и
реальный шелл пользователю на android-таргете» и «на linux-таргете» это два
разных решения, а не одно на весь образ. По умолчанию есть смысл включать
только на linux-таргете (открытый интерактивный шелл на Android-appliance —
лишняя площадь атаки, не то, ради чего его держат), но это осознанный
выбор, который должен зафиксировать provision-манифест (§7) явно — юнит-
enablement per-target, а не побочный эффект общего rootfs.

**Наблюдение из код-ревью фазы 0 (ревизия 5).** В незакоммиченном diff'е на
момент ревью `multi-user.target.wants/{andler-display-resolution,
qemu-guest-agent}.service` уже удалены, без встречной enablement-правки —
похоже на начало именно этой работы, но не хватает контекста понять,
доделана ли она. Перед коммитом стоит явно проверить: если это per-target
enablement, у обоих юнитов должен появиться эквивалент на каждом таргете,
где они нужны (оба нужны и на `android.target` — `guest os up`/`waydroid
ready` из §A зависят от QGA независимо от boot-mode); если это
недоделанный побочный кусок — откатить перед мёржем, а не оставлять оба
юнита не стартующими ни на одном таргете.

**РЕШЕНО (фаза 0, ответ на находку 3 ревизии 5):** diff с удалением
`multi-user.target.wants/{andler-display-resolution,qemu-guest-agent}.service`
в фазу 0 не входил — в финальном рабочем дереве фазы оба юнита на месте и
включены на всех таргетах (проверено: `git status` чистый, `git log
--diff-filter=D -- scripts/` не показывает их удаления; ветка
`refactor/phase0-foundations` содержит только удаление `scripts/start.sh`
из более раннего коммита `334dd02`, не относящегося к фазе). Per-target
enablement (sshd/реальный шелл только на linux-таргете) остаётся в фазе 2
вместе с §B — это осознанное решение, а не незавершённый кусок.

**Готовность как предусловие, не гонка.** `andler connect` не долбит ssh/adb
до успеха вслепую — он ждёт контракт гостя из §A (`serial up → qga up →
display applied → guest os up`) и только после нужного уровня готовности
пробует следующий уровень доступа; если готовность не достигнута за бюджет
времени — честная ошибка с указанием, на каком уровне контракта гость
завис (не «ssh: connection refused» без контекста).

**Креденшелы и безопасность.** Baked host-ключ — часть образа/provision, не
секрет, генерируемый на лету, но у него должен быть дом и жизненный цикл,
которых в первом черновике не было:

- **Один ключ на host-пользователя (не на инстанс).** Первый черновик
  предполагал ключ на инстанс ради многопользовательских сценариев (§H) —
  но это смешивает два разных измерения: приватный ключ никогда не попадает
  в гостя (в `authorized_keys` уходит только публичная часть), поэтому
  компрометация одного гостя не раскрывает ключ хоста независимо от того,
  общий он или нет. Изоляция между host-пользователями и так уже есть —
  каждый host-пользователь гоняет свой `andlerd` со своим `ANDLER_HOME`
  (см. `scripts/andlerd.service`, per-user unit). Ключ на инстанс добавляет
  ротацию/хранение N ключей вместо одного без реального выигрыша в
  безопасности — это оператор-идентичность («я подключаюсь к своим VM»), а
  не секрет конкретной VM.
- **Место и права**: `$ANDLER_HOME/ssh/id_ed25519` (+ `.pub`), генерируется
  один раз при первом использовании `andler connect`/provision, `0600` на
  приватную часть — та же дисциплина, что и для остального
  `ANDLER_HOME` (`ensure_private_dir`, уже есть в коде для store-пути).
- **Ротация**: если ключ когда-то придётся заменить, у уже прогретых
  образов `authorized_keys` сам себя не обновит — это online-мутация
  гостя через тот же `GuestMutator` (§6), что и остальные мутации, не
  отдельный механизм. `andler connect --rotate-key` (или аналог) —
  провизионирует новый публичный ключ через QGA/guestfs, затем меняет
  активный ключ хоста; старый ключ хранится до подтверждения, что новый
  работает на всех живых инстансах, чтобы не потерять доступ к VM, которая
  в этот момент выключена и не может быть провизионирована немедленно.

Порт-форвардинг — `network.port_forwards = [{host_port, guest_port}]`,
выделение host-портов не должно конфликтовать между параллельно запущенными
инстансами (тот же класс проблемы, что порты SDL/display в §H, — решать
одним механизмом аллокации портов, не двумя).

**Объём и фаза**: `network.port_forwards` — конфиг (§1, key-path);
provision baked-key — манифест (§7, GuestMutator); эффективный профиль
(`kind`×`boot_mode`, находка ревизии 4) — `boot_mode` переезжает в
`instance.toml` тем же key-path механизмом, что и остальные поля (§1, P31),
вместо офлайн-mount на каждый запрос; `andler connect` — CLI-команда поверх
готовых RPC (console — почти готов, ssh/adb — port-forward + provision).
Поднято в фазу 2 (см. таблицу фаз) вместо фазы 3-4, потому что не зависит от
GuestMutator/libguestfs — только от provision одного файла (ключ) через
существующий QGA-путь, который работает уже сейчас; перенос `boot_mode` в
конфиг зависит только от фазы 1 (TOML), не от фазы 2 — может уйти туда же,
если удобнее по потоку работы.

### C. Долгие операции: прогресс и отмена
`guest install` (минуты), clone 256GiB (долго), snapshot/compact — сейчас без
прогресса, Ctrl-C не отменяет RPC (операция продолжается на daemon'е).
Решение: прогресс в streaming RPC (существующий паттерн metrics/logs) +
токен отмены (cancel RPC или drop-семантика соединения); для клиента — тот же
уровень, что у translator download (уже есть прогресс).

### D. Атомарность и восстановление после сбоя
Цепочки (снапшот = файл + метаданные), конфиг (tmp+rename), create (guard уже
есть), clone. Правило: **порядок операций таков, что файлы валидны в любой
момент; метаданные — последний шаг**; при старте daemon — реконсиляция
(chain ↔ SQLite ↔ toml: осиротевшие слои, незавершённые операции = журнал
операций, если нужен). Разработать до фазы 5.

### E. gRPC: идемпотентность, retry, авторизация
- Сетевых клиентов нет (127.0.0.1), но: повторный `start` при network-retry
  клиента не должен делать двойное действие — идемпотентность или явные
  конфликты (FSM уже даёт). Решение: идемпотентные RPC для lifecycle.
- **Авторизация локального IPC — решить сейчас, не откладывать до
  «не-127.0.0.1» (находка ревизии 4, проверено по коду).**
  `ANDLERD_LISTEN_ADDR` сегодня — уже TCP-сокет (`apps/daemon/src/main.rs`),
  не unix-сокет; `127.0.0.1` ограничивает сеть, но не пользователя — на
  многопользовательском хосте любой локальный пользователь коннектится на
  порт демона без проверки, кто он, независимо от того, что «каждый
  host-пользователь гоняет свой `andlerd`» (§12.B) — ничто это не
  проверяет на уровне сокета. Явный выбор одного из двух (см. §13.16, §L):
  (a) зафиксировать «один host-пользователь на машину» как допущение — тогда
  сегодняшнее поведение осознанно достаточно; или (b) unix-сокет по
  умолчанию (`$XDG_RUNTIME_DIR/andler/daemon.sock`, `0600`, тот же паттерн,
  что уже есть у `qmp.sock`/`qga.sock`), TCP — опция для явно сетевых
  сценариев. Не решать это явно — значит выбрать (a) по умолчанию, но
  неявно.

### F. Логи: ротация и retention
`qemu.log`/`console.log` растут без ограничений (сессия: 4.4GB диск, логи —
бесконечно). Решение: rotation по размеру/количеству (logrotate-стиль, в
daemon), retention для `~/.andler/logs`.

### G. Дисковое пространство
qcow2 тонкий рост (уже есть trim_on_shutdown/compact), но: GC кэша базовых

### H. Multi-instance ресурсы

### I. Display/GPU: решение-таблица
Выбор `render_backend` (venus/virgl/vfio) и display-движка по вендору GPU

### J. Сеть

**Уточнение состояния (проверено по коду, не по описанию в первом
черновике)**: NAT и Bridge — рабочие; **Isolated — не реализован**, это
осознанная заглушка (`services/andler-net/src/lib.rs`, `setup_isolated`),
возвращающая честную ошибку вместо повторения прошлой опасной попытки
(предыдущая версия роняла весь входящий трафик хоста и не давала реальной
изоляции — см. комментарий в коде и обновлённый `AGENTS.md`, Code Comments
Policy). Открытые вопросы первого черновика подразумевали, что все три
режима «есть» — это неточность плана, не кода. Настоящая изоляция требует
network namespace + veth-пару и QEMU, заспауненный внутри namespace (`ip
netns exec`) — `process.rs` сегодня про namespace ничего не знает. Если
Isolated не берётся в явную фазу — вписать в non-goals (§13.16) как «не
реализовано, а не сломано», чтобы никто на фазе 2-3 не тратил время, решив,
что наткнулся на регрессию.

**Найденный и не учтённый пробел: «ноль root» не покрывает Bridge.**
`setup_bridge` (`services/andler-net/src/lib.rs:82-84`) вызывает `ip link
add <iface> type tap` и `ip link set <iface> master <bridge>` напрямую, не
через helper — а это требует `CAP_NET_ADMIN`, которого у обычного
пользователя по умолчанию нет (`geteuid`/`is_root`-проверки в коде нет
вообще — ошибка просто всплывёт сырой из `ip`). Весь пафос «ноль root» в
плане (§6, §18) сегодня покрывает только офлайн-мутации гостя (helper/
sudoers/nbd), не сеть. **Решение (явное, не оставлять открытым)**: NAT —
единственный по-настоящему zero-root режим, это фиксируется в §18 как факт
per-режим, а не бланково; Bridge документируется как требующий
одноразового `setcap cap_net_admin+ep $(which andlerd)` при установке (или
`AmbientCapabilities=CAP_NET_ADMIN` в user-unit, если он там вообще
применяется — проверить) — `andler doctor` получает явную проверку
capability на бинарнике и понятную инструкцию, если её нет, вместо сырого
`EPERM` от `ip`.

Остальное без изменений: добавить port-forward (§B), DNS для гостя
(реализуется через resolv.conf — уже есть механизм), teardown при сбое
(существует для bridge tap). Паттерны passt vs slirp — решение
зафиксировать.

### K. Обновление самого ANDLER
schema_version (есть в §1), миграция store, совместимость proto (аддитивные
поля ок) — но добавить: `andler doctor` проверку версий (guestfs-tools,
qemu) и миграционный чек. **Рестарт daemon убивает VM** больше не
принимается как данность — см. §2.5 (reconnect по QMP-сокету +
pidfd-ожидание); если по итогам спайка фазы 0 полный reconnect не тянет,
суженный вариант там же (демон хотя бы находит и явно завершает сирот,
вместо того чтобы терять их из виду).

### L. Безопасность (Security/Threat Model — новый раздел, не «v2»)
`docs/ROADMAP.md` (пункт про `andler-helper`) ссылается на threat model
«documented honestly in `docs/ARCHITECTURE.md`» — по факту там сегодня нет
ни одного упоминания темы (проверено grep'ом, находка ревизии 4): это не
обновление существующего раздела, а его первое появление, и заодно —
починка уже висящей ссылки в `docs/ROADMAP.md`, указывающей в пустоту.
Содержание раздела: после удаления root (§6) граница = QEMU (VM изолирована),
daemon под пользователем; граница IPC = решение §12.E (кто вообще может
подключиться к демону, не только что демону разрешено делать
подключившемуся); гости недоверенные (снапшот может быть битым, манифест —
вредоносным): валидация манифестов, лимиты (время/размер); допущение об
одном host-пользователе на машину (§13.16), если оно принято, — тоже часть
threat model, а не только пункт в таблице non-goals.

### M. Матрица поддержки гостей
Linux (Arch-образ, ISO-установки) и Android (waydroid 11/13, vanilla/gapps,
microg): контракт гостя (§A) + пакетные менеджеры (3 шт.) + boot-mode — как
явная матрица «что гарантируется для какой ОС», чтобы не было «а у меня не
работает» без ответа.

### N. Резервное копирование
Инстанс = каталог (qcow2+toml+VARS) — backup тривиален; экспорт существует
(clone export). Решение: документировать процедуру + `andler doctor` проверку
целостности (qcow2 check).

### O. Автозапуск инстансов
При старте daemon всё в Stopped. Опция `autostart` в конфиге инстанса —
решить «да/нет» и поведение при сбое (не рестартовать в цикле).

### P. Тест-глубина
Live-snapshot под нагрузкой записи (фазa 5), clone при запущенной VM,
guestfs-операции на повреждённом диске (честные ошибки), E2E для каждого
нового RPC.

## 13. Guardrails: что нельзя сломать по пути (контракты рефактора)

Это не фичи, а инварианты — рефактор обязан их сохранить или менять явно, с
миграцией и обновлением тестов/доков в том же коммите.

1. **Wire-контракт QEMU-командной строки.** В `cmdline.rs` есть перекрёстные
   зависимости (chardev/device id, порядок: clipboard добавляет
   virtio-serial-pci, на который ссылается vdagent; сокеты `*.qmp.sock`/
   `*.qga.sock`; fw_cfg-ключи разрешения). Разбивка на секционные билдеры
   обязана сохранить id-схему и имена сокетов — golden-тесты сравнения
   cmdline с эталонными конфигами это пиннят; менять можно только вместе с
   ними.
2. **Дисциплина convert.rs** (1692 строки, bidirectional): `UNSPECIFIED` →
   `ConvertError::MissingField`, никаких тихих дефолтов (правило репо).
   Любое изменение доменных типов (§1, §8) проходит через конвертер в обе
   стороны + roundtrip-тесты.
3. **Стабильность on-disk layout и id-схемы.** Пути `~/.andler/instances/
   <64hex>/`, `~/.andler/cache/`, `$XDG_RUNTIME_DIR/andler/qmp/<id>.sock`,
   env-контракт `ANDLERD_*`/`ANDLER_HOME` — держать; старые инстансы обязаны
   загружаться (миграция конфига §1 — не «если toml нет, бери БД», а явная
   одноразовая конвертация с отказом при неоднозначности).
4. **Текст ошибок — контракт.** E2E-сьюты грезят сообщения
   (`expect_out_grep`), CLI печатает их пользователю. Изменение формулировок —
   осознанно, с обновлением e2e-ассертов в том же коммите.
5. **Паритет `andler doctor`.** Список проверок — документированный контракт
   (docs/API.md). После §6: проверка nbd-модуля уходит, появляется проверка
   guestfs-tools; после удаления helper — проверки sudoers/helper исчезают.
   Обновлять вместе с архитектурой, не по остаточному принципу.
6. **`andler-core` остаётся без I/O и без workspace-зависимостей.** Это
   несущий инвариант для офлайн-тестирования. GuestMutator, DiskChain,
   resolver — **типы и trait'ы в core, реализации в services/backends**.
   Иначе core перестанет быть чистым и тесты потеряют «работает без QEMU».
   **Явное решение (закрывает открытый вопрос)**: `HypervisorBackend` и
   новые trait'ы существуют ради тестируемости (fake-реализации в юнит-
   тестах) и разделения ответственности — **не ради гипотетического
   второго гипервизора**. QEMU — единственный поддерживаемый бэкенд на
   обозримое будущее (крейт называется `andler-qemu`, cmdline/QMP-специфика
   пронизывает код насквозь). Практическое следствие: не проектировать
   абстракции «на случай libvirt/cloud-hypervisor» — если сигнатура
   trait-метода удобнее с QEMU-специфичным понятием (например, `device_id`
   в терминах `device_add`), это нормально, лишний слой ради
   гипотетического второго бэкенда — это переусложнение без пользователя.
7. **Сериализация операций на инстанс.** Два RPC на один инстанс
   (config set + start, snapshot + clone) не должны перемежаться на диске:
   per-instance op-mutex (single-writer для цепочек) — часть супервизора §2
   и DiskOps §8. Без этого крэш-безопасность §D недоказуема.
8. **Таймауты для новых внешних процессов.** guestfish/virt-customize на
   битом образе могут висеть (appliance boot) — обязательный connect+total
   timeout и killability (правило репо об I/O-таймаутах).
9. **Бюджет латентности read-only офлайн-операций.** `guest list`/
   `boot-mode get` на остановленной VM не должны стоить полного appliance
   boot каждую команду — решить: кэш/одноразовый запуск на пакет операций
   или принятый бюджет в секунды. Зафиксировать в acceptance фаз 3-4.
10. **Семантика `remove --purge` с цепочками.** Удалять: активный слой,
    слои снапшотов, метаданные, VARS, логи, сокеты. Не трогать: файлы вне
    каталога инстанса (дополнительные диски). Осиротевшие слои после крэша —
    реконсиляция §D.
11. **Graceful shutdown daemon'а.** SIGTERM: остановить супервизоры, убить
    QEMU-детей (kill_on_drop), флаш метаданных снапшотов; тестируемо.
12. **Централизация знаний о layout гостя.** Пути waydroid-образа
    (`etc/waydroid-extra/images/system.img`, `var/lib/waydroid/overlay`) —
    один модуль (AndroidGuestLayout), а не три модуля с копиями.
13. **Конструкторы тестового daemon'а** (`Daemon::new`/`with_store`/
    `restore`) используются всей тестовой инфраструктурой — смена источника
    реестра (§1) мигрирует их вместе с тестами, не оставляя два пути
    создания.
14. **Семантика broadcast-стримов** (metrics/logs): медленный клиент не
    должен ронять других; lag-политика фиксируется и покрывается тестом.
15. **env/unit/install-контракт**: `ANDLERD_*` переменные, scripts/
    andlerd.service, install.sh/uninstall.sh — обновляются синхронно с
    изменениями (store-path → snapshots, doctor checks). Включая смену
    дефолта `ANDLERD_LOG_FORMAT` на structured JSON (§9.1 — сегодня дефолт
    человекочитаемый, JSON опционален; план меняет их местами, находка
    ревизии 4): таблица Environment Variables в `AGENTS.md` и
    `docs/CHANGELOG.md` (Changed) обновляются вместе с кодом — это смена
    поведения по умолчанию, а не только внутренняя деталь логирования.
16. **Матрица non-goals**: Windows/BSD-гости, ANDLER_HOME на NFS — явно
    вне скоупа, чтобы рефактор не «улучшал» их по пути. **Isolated-режим
    сети (§12.J)** — туда же, если явно не берётся в отдельную фазу: это
    осознанная нереализованная заглушка (не регрессия рефактора), и
    `docs/ROADMAP.md` должен говорить это прямо, а не оставлять
    угадываться по коду. **Многопользовательский хост (§12.E, находка
    ревизии 4)** — тоже должен получить явную строку здесь: либо «один
    host-пользователь на машину» зафиксировано как допущение, либо это не
    non-goal, и тогда авторизация локального IPC — не факультативный пункт
    §12.E, а требование той фазы, где меняется транспорт демона.
17. **API-стабильность на время рефактора**: proto/CLI-изменения — только
    аддитивные (новые RPC/поля/флаги), пока не завершены все фазы; ломающие
    изменения — одним финальным шагом с миграцией и обновлением всех доков.
18. **Контракт логирования (§9.1) — не деградирует по ходу рефактора.**
    Любой новый RPC/операция обязаны нести `request_id`/`op_id` в span с
    первого коммита, а не «добавим логи потом»; ревью каждой фазы включает
    проверку: новый код проходит через structured-логирование, а не через
    `println!`/голый `tracing::info!` без полей корреляции. Это единственный
    guardrail, который не защищает существующее поведение, а требует нового
    — потому что «качественное логирование» иначе тихо откатится к
    состоянию первого черновика (P27) по ходу больших фаз 3-6.
19. **Version-handshake CLI↔daemon.** Рефактор растягивается на много фаз
    и много пересборок — обычный бытовой случай: демон пересобран на фазе
    2, CLI — ещё нет (или наоборот, забыт `systemctl --user restart
    andlerd`). Сегодня это проявляется как непонятная ошибка десериализации
    где-то посреди RPC. Минимум: `ServerInfo`/`Version` RPC (или поле в
    каждом ответе), CLI сверяет перед выполнением команды и говорит явно
    «demon версии X, CLI ждёт Y, перезапусти demon» вместо непрозрачной
    ошибки protobuf. Как и №18 — это guardrail, требующий нового кода, а не
    защищающий существующее поведение; добавлять с фазы 2 (там же, где
    CLI/daemon resolver, §4), пока рефактор ещё не породил первое реальное
    расхождение версий на практике.
20. **Порождённый фоновый таск обязан быть наблюдаемым, а не
    fire-and-forget** (находка ревизии 5, код-ревью фазы 0). Голый
    `tokio::spawn(...)` с отброшенным `JoinHandle` означает, что паника
    внутри таска не логируется и не восстанавливается — вызывающий код рано
    или поздно увидит деградацию (закрывшийся канал), но не узнает, что
    случилось и когда. Найдено на практике в фазе 0: `spawn_supervisor`
    (§2.4) — ровно тот паттерн «fire-and-forget spawn», который R2 уже
    называл риском для тёплого guestfs-appliance (§6.2), — один и тот же
    класс проблемы, обнаруженный дважды в разных местах плана, что делает
    его правилом, а не разовой правкой. Любой `tokio::spawn`, который
    держит состояние инстанса, appliance-процесс или любой другой ресурс
    дольше одного RPC-вызова, обязан либо (a) сохранять `JoinHandle` и явно
    логировать/обрабатывать его завершение (в т.ч. паникой), либо (b) идти
    через `JoinSet` с политикой рестарта — то, что §2.4 уже требует для
    metrics-подзадачи. Голый отброшенный `JoinHandle` допустим только для
    тасков короче одного RPC, где закрытие канала и есть достаточный сигнал
    вызывающей стороне.

## 14. События, операции и прогресс: шина + модель операций (новое ядро UX)

### Зачем (ответы на прямые вопросы)

- **«Нужно ли daemon'у слать подробные отчёты своих действий?»** Да. Сейчас
  «что произошло» — только текстовые логи и косвенные признаки (пользователь
  узнал о крахе hwc по глазам). Нужен единый поток событий.
- **«Можно ли узнать, что произошло?»** Да — событийный аудит на инстанс,
  переживающий рестарт.
- **«Можно ли выводить прогресс?»** Да — модель операций с фазами и весами;
  те же каналы, что у metrics/logs.
- **«Можно ли несколько запросов и ничего не ломается?»** Да — очередь
  операций на инстанс + идемпотентность; это и есть гарантия конкурентности.

### Источники событий

1. **QMP-события гостя** (сегодня QMP-клиент их игнорирует — только
   запрос/ответ):
   - `VSERPORT_CHANGED` → готовность QGA (уровни §A) — мгновенно, без проб;
   - `SHUTDOWN`/`RESET`/`POWERDOWN` → чистое завершение/перезагрузка —
     FSM-переход без 30-секундного health-поллинга;
   - `DEVICE_DELETED` → подтверждение detach (сейчас retry-поллинг в
     hotplug-коде — событие заменяет его);
   - `BLOCK_IO_ERROR`/`BLOCK_JOB_*` → ошибки диска/снапшотов с причиной;
   - `GUEST_PANICKED`/`WATCHDOG` → Error с причиной;
   - `STOP`/`RESUME` → паузы/возобновления.
2. **Супервизор** (§2): выход процесса (код, чисто/аварийно), FSM-переходы,
   рестарты фоновых задач.
3. **Операции**: фазы, прогресс, завершение/ошибка/отмена.
4. **GuestMutator**: прогресс офлайн-операций (staging N/M).

### Модель

```
DaemonEvent { ts, instance_id: Option,
  kind: Lifecycle{from,to,reason}
      | Operation{op_id, kind, phase, progress(0-1), state, error}
      | Qmp{event, data}
      | Readiness{level}          // §A
      | Log{level, message} }

Operation { op_id (uuid), instance_id, kind (create/clone/guest-install/
            snapshot/compact/…), phases: [(name, weight)], progress,
            state: Queued|Running|Done|Failed|Cancelled, error }
```

### Транспорт и UX

- **Шина**: daemon-wide `tokio::broadcast` (паттерн metrics/logs уже есть);
  slow-client политика — §13.14.
- **RPC `StreamEvents(instance filter)`** → CLI: `andler events [<id>]
  [--follow] [--json]`; `andler op status <id>` показывает очередь операций.
- **Аудит, переживающий рестарт**: `~/.andler/instances/<id>/events.jsonl`
  (append-only, ротация §F) — «что произошло с инстансом» доступно всегда.
  **Пишет сама операция** (авторитетный источник), а не подписчик шины: так
  переполнение broadcast (drop у медленных потребителей) не создаёт дыр в
  аудите; шина — только для живых потребителей (CLI/прогресс).
- **Прогресс в CLI**: долгие операции (guest install, clone, snapshot,
  compact) рисуют прогресс по фазам из Operation-событий.
- **Отмена**: `andler op cancel <op_id>` — cooperative token через операцию
  (guestfs — убить appliance, clone/compact — прервать процесс), не SIGKILL
  вслепую.
- **Конкурентность**: per-instance очередь — один долгий op на инстанс
  (single-writer §13.7, реализуется супервизором — §2.4), остальные ждут;
  глобальные операции (doctor, list) параллельны.
- **14.1 Идемпотентность — явный ключ, не «тот же kind».** Join к
  существующей операции происходит, только если совпадает **(kind,
  нормализованные аргументы)**, а не просто kind: `snapshot create tag=a` и
  `snapshot create tag=b` на одном инстансе — разные ключи → второй запрос
  либо ставится следующим в очередь, либо получает `Conflict`, если kind
  логически несовместим с параллельным выполнением (например, `restore` не
  может ждать своей очереди за `snapshot create`, если снапшот ещё не
  создан — такие пары фиксируются как явно несовместимые в реализации
  очереди, а не выясняются как race). Для точной идемпотентности при сетевом
  retry клиента (§E, «повторный `start`») — опционально client-provided
  `idempotency_token` в metadata RPC, join по нему приоритетнее join по
  аргументам.

### Объём и фаза

Примитивы (DaemonEvent, Operation, broadcast) — фаза 0 (на них строятся
супервизор и всё остальное); QMP-подписка + StreamEvents/CLI — фаза 3
(с супервизором); events.jsonl — фаза 1; прогресс-отмена долгих RPC — фаза 2.

## 15. Ресурсные лимиты: CPU pinning, memory overcommit

### Проблема

Конфиг уже несёт `cpu.cores/sockets/threads/priority`, `memory.size_bytes/
ballooning/ksm/zram`, но: pinning'а нет, overcommit не управляется, host-
топология в `verify`/`doctor` не сверяется с запросом.

### Решение

- **Конфиг** (§1, key-path): `cpu.pinning = [vcpu→host]` или `auto` (NUMA-аккаунт
  по host-топологии), `cpu.priority` расширить (Normal/Realtime), `memory.
  overcommit` (QEMU `-overcommit mem-lock=on` — mlock, запрет swap) и политика
  hugepages.
- **cmdline** (§11): `-object thread-context,cpu-affinity=…` (QEMU 8+), `-mem-
  prealloc` при overcommit, balloon уже есть.
- **doctor/verify**: host-топология (nproc/NUMA/RAM, свободные CPU), валидация
  pinning-набора, предупреждение при overcommit без достаточной RAM.
- **cgroups v2** (опциональный слой): инициализация через systemd user-слайс
  (cpu.weight/memory.max) — только если делегирование доступно; не блокер.
- Фаза: после ядра (конфиг+cmdline) — фаза 8 вместе с multi-instance (§H).

## 16. CLI-фичи из ROADMAP: шаблоны VM и экспорт OCI

### Шаблоны VM (quick VM creation)

- `~/.andler/templates/<name>.toml` — **фрагменты** `InstanceConfig`
  (partial): merge-порядок defaults < template < флаги < `--file` <
  `config set`; валидация — тем же resolver'ом (§4), шаблоны не обходят
  валидацию.
- CLI: `andler create --template gaming` (+ встроенные: desktop/android-
  gaming/headless); wizard предлагает шаблоны как пресеты (уже есть
  «recommended settings» — обобщается).
- Фаза 2 (resolver уже там).

### Экспорт VM как OCI-контейнера

- `andler export <id> --oci <dir>`: read-only конвертация **Linux**-гостя в
  OCI layout: guestfs `tar-out` rootfs + `config.json` (arch, entrypoint
  `/sbin/init`). Android — не поддерживается (не осмысленно). Требует
  GuestfsMutator (фаза 4+). Низкий приоритет — фаза 8.

## 18. Критерии завершения (когда «архитектура переделана»)

- **Ноль root — по режимам, не бланково**: andlerd работает без sudoers и
  helper для офлайн-операций гостя (GuestfsMutator); `andler doctor` не
  проверяет nbd/sudoers. NAT-сеть — без root. Bridge-сеть — документированно
  требует одноразового `setcap cap_net_admin+ep` (§12.J), `doctor` явно
  проверяет и объясняет, не падает сырым `EPERM`.
- **Рестарт демона не убивает VM без необходимости** (§2.5): reconnect по
  QMP-сокету восстанавливает FSM-состояние живых инстансов **для того
  сценария, который мотивировал раздел — обычный graceful-рестарт, не
  только крах** (R9 закрыт явным решением, не оставлен неочевидным
  следствием несогласованных кусков кода); если pidfd-подход не прошёл
  спайк (R8) — минимум, демон не теряет из виду осиротевшие процессы молча.
- **Один источник конфига**: нет `config_json`; `config edit` работает;
  `config status` корректен для ручных правок на запущенной VM.
- **Снапшоты внешние**: create/restore/delete/list через цепочку слоёв;
  discard — дефолт restore, старые внутренние снапшоты читаются; метаданные
  — только в store.
- **События**: `andler events` показывает lifecycle/QMP/операции; events.jsonl
  переживает рестарт; очередь операций гарантирует single-writer.
- **Логирование** (§9.1): сквозная корреляция `request_id`/`op_id` от CLI до
  QMP-байта работает для каждого RPC, не только для новых; `andler logs
  daemon` показывает structured-вывод без похода на файловую систему.
- **Доступ**: `andler connect <id>` работает для console/ssh (Linux)/adb
  (Android) с автовыбором уровня (§12.B); SSH host-ключ живёт в
  `$ANDLER_HOME/ssh/`, не персистится в открытом виде нигде ещё.
- **Version-handshake** (§13.19): CLI обнаруживает несовместимую версию
  demon'а явной ошибкой, не сырым protobuf-сбоем.
- **Бюджеты** (замеряются e2e/bench): `start` ≤ 3с; `status`/`list` (50
  инстансов) ≤ 500мс; `guest list` офлайн ≤ 2с (тёплый appliance); конфиг-
  команды ≤ 100мс.
- **Гейт**: workspace build/test/clippy/fmt зелёные; все e2e-сьюты зелёные;
  `--ignored` интеграционные — в CI; каждая фаза смёржена в `main` по
  правилам ветвления из `AGENTS.md` (fast-forward/rebase, не squash).
- **Threat model существует, не только упоминается** (находка ревизии 4):
  `docs/ARCHITECTURE.md` содержит реальный раздел Security/Threat Model
  (§L) — сегодня там нет ни одного упоминания темы, только ссылка на него
  из `docs/ROADMAP.md`, указывающая в пустоту; IPC-авторизация решена явно
  (§12.E), не оставлена как «когда-нибудь, если не 127.0.0.1».
- **GuestMutator-бэкенды проходят общий конформанс-набор** (находка ревизии
  4, §6): `QgaMutator` и `GuestfsMutator` дают одинаковый наблюдаемый
  результат на одинаковых операциях — не только каждый по отдельности
  покрыт тестами.
- **Доки**: README/API/GRPC_API/ARCHITECTURE/crate-README/e2e-README/CHANGELOG
  отражают целевую архитектуру; ROADMAP без выполненных пунктов в In Progress;
  план рефакторинга удалён из репозитория целиком (не пуст — удалён), и
  `grep -ri` по репозиторию (код, доки, `AGENTS.md`) не находит ни одной
  ссылки на его имя.

## Как проводится сам рефакторинг

Общие, постоянно действующие правила — ветвление, коммиты, требования к
комментариям, порог на размер модуля — теперь в `AGENTS.md` (см. разделы
**Branching**, **Code Comments Policy**, **Refactoring Discipline**; они
действуют для всего репозитория, не только для этого рефакторинга). Здесь —

### Ветка на фазу, привязанная к номеру в этом файле

`refactor/phaseN-<slug>` — номер и слаг берутся прямо из заголовка фазы в
таблице ниже (`refactor/phase0-foundations`, `refactor/phase1b-diskchain`
и т.д.), не придумываются заново. Это делает `git log`/`git branch -a`
навигируемыми по этому документу без дополнительного маппинга.

### Commit message — фаза видна в истории

Поверх Conventional Commits из `AGENTS.md`: коммит, реализующий пункт этого
плана, называет фазу и номер пункта в теле (не обязательно в subject, чтобы
не раздувать 72-символьный лимит) — по номеру и слагу фазы, **не по имени
этого файла** (он временный и будет удалён, см. Ревизию 4): `refactor(daemon): supervisor owns op-queue

Implements Phase 2 (resolver-access), §2.4.` — так `git log --grep 'Implements Phase'`
показывает прогресс по фазам, а после удаления этого файла коммит остаётся
понятным сам по себе (фаза и номер пункта — не путь к файлу, который скоро
исчезнет). Когда пункт фиксирует постоянный контракт, коммит дополнительно
указывает итоговый файл: `..., §6.1 — see docs/ARCHITECTURE.md#guestmutator.`

### Стратегия дробления коммитов по фазам (решено на ревью 1b)

Один логический коммит на фазу — когда кусочки плотно связаны и промежуточные
коммиты не собираются (прецедент: фаза 1b, 35 файлов / 2581 вставка одним
коммитом — schema v3 без snapshot_ops и qcow2-примитивов не имеет смысла,
дробить значило бы коммиты, которые сами не проходят гейт). Исключение —
фазы с высоким риском регрессии, где `git bisect` на конкретный шаг важнее
компактности истории: **фаза 4 (снос helper/sudoers) дробится по принципу
«один легин-механизм / одно sudoers-правило за коммит»**, каждый коммит
сам по себе проходит гейт (удаляет путь, мигрирует доки/doctor/e2e этого
пути) — так регрессия привилегий указывает на точный шаг, а не на весь
снос. Прочие фазы решают по тому же критерию перед началом: связанность →
один коммит, bisect-ценность → дробление.

**Первым шагом фазы 4** (до любого кода): перечислить в этом документе
текущий список команд `apps/helper` и sudoers-правил поимённо (в ROADMAP
уже зафиксировано «10 строк sudoers → 1» — список конечный и известный)
— тогда «один механизм/правило за коммит» сразу становится чек-листом с
галочками, а не абстракцией, которую придётся заново разбирать по коду в
момент старта фазы.

### Снижение root для package-операций — план (фаза 5, ревизия 5)

**Цель**: root на хосте становится нужен только для «VM не загружается
вообще» (редкий rescue), а не для любой установки пакета. Уточнение к
более ранней формулировке «онлайн, пока VM запущена»: большинство VM
выключены не потому что сломаны — chroot остался бы обычным путём.
Поэтому:

1. **Онлайн-путь через QGA — дефолтный.** [DONE fac33a0] VM запущена и QGA
   отвечает → `guest-exec` запускает команды из `core/package_manager.rs`
   (единый источник для online и offline путей) внутри гостя; root —
   гостевой. Установка в остановленную VM идёт через supervisor op
   (фазы: starting VM → waiting for guest agent → install → stopping VM,
   cancelable, видна на событийной шине); `wait_for_guest_exec`-паттерн
   (guest-exec + poll exit + stderr при неудаче) уже используется
   `guest_exec_package` в andler-qemu. Остаток: online-путь при уже
   запущенной VM — пока блокирующий RPC (как до фазы 5); обернуть в op —
   будущий improvement, не блокер.
2. **Автозапуск для обслуживания.** [DONE fac33a0] Демон тихо стартует
   остановленную VM без дисплея, ждёт QGA (таймаут `ANDLERD_GUEST_AGENT_WAIT_SECS`,
   default 120s), ставит/снимает пакет, гасит обратно; при отсутствии QGA —
   честная ошибка с hint на `--offline`. `--offline` (новый флаг CLI +
   поле proto) форсирует qemu-nbd/chroot — rescue-случай. `--offline` при
   запущенной VM — отказ с объяснением.
3. **Курица-и-яйцо.** [ПРОВЕРЕНО] `qemu-guest-agent` + systemd-юнит
   запечены в Android-базовый образ (`docker/images/base/Dockerfile:73`,
   `rootfs/etc/systemd/system/qemu-guest-agent.service`) — свежая Android-VM
   обслуживается онлайн с первой установки. Для Linux-инстансов
   (пользовательский образ) авто-путь честно падает на таймаут QGA с hint.
4. **Определение пакетного менеджера онлайн.** [DONE — уже было в andler-qemu]
   `guest_exec_package` пробирует apt-get/dnf/pacman скриптом через
   guest-exec и берёт команды из `core::package_manager` (тот же источник,
   что offline).
5. **Спайк (user-namespaces + FUSE) — [ВЫПОЛНЕН, УСПЕХ, 2026-08]**: убрать
   root из offline-случая через `guestmount` (FUSE, без root) + `unshare
   --user --map-root-user --mount` + chroot. Критерии проверены на реальном
   Debian rootfs (debootstrap bookworm, e2e-контейнер):
   - `guestmount -a disk.img -m /dev/sda /mnt` — монтирует qcow2 БЕЗ root
     (блочный mount в userns не нужен — FUSE его заменяет);
   - `unshare --user --map-root-user --mount` + `chroot /mnt` — работает;
   - **apt-get update + install -y hello — УСТАНОВЛЕН** (`Status: install ok
     installed`) при `APT::Sandbox::User=root` (apt-метод setuid(_apt)/
     setgroups запрещены в userns — это единственный обход, найден
     через Debug::Methods=1) и `Acquire::ForceIPv4=true` (IPv6-first
     давал 112 ECONNRESET в контейнере);
   - Ограничения: chown на FUSE — EINVAL (apt-логи: term.log chown warn,
     некритично; пакеты со setuid-битами/chown в postinst могут
     работать не полностью); dpkg-статус пишется нормально.
   **Перепроверка без привилегий (2026-08, свежий архив)**: три среды, полные
   логи:
   - Контейнер без privileged (`E2E_PRIVILEGED=false`; и `--cap-drop=ALL
     --no-new-privileges`): `unshare --user` → EPERM при default seccomp;
     при `seccomp=unconfined` unshare-вызов проходит, но падает
     `write /proc/self/uid_map: EPERM` — ядро разрешает unprivileged
     userns-создание только не-root uid, а процесс контейнера — root без
     капс (unprivileged-путь для uid 0 требует CAP_SETUID); guestmount-
     appliance (QEMU supermin) тоже требует капс → FUSE_FAIL. Всё —
     контейнерная специфика, не модель пользовательского хоста.
   - Хост, uid=1000, без sudo, обычный набор капс (и даже под seccomp-
     фильтром, seccomp=2): полный цикл — guestmount FUSE_OK + unshare +
     chroot + `apt-get install hello` → `Status: install ok installed`
     (HOST_RC=0). Единственный warn — chown term.log EINVAL (FUSE).
   **Вывод**: интеграция = zero-root на типовом пользовательском хосте без
   одноразовой настройки (Arch-подобные); на Debian/Ubuntu предусловие —
   `sysctl kernel.unprivileged_userns_clone=1` — проверить в doctor при
   интеграции. Контейнерные sandbox'ы не модель хоста. Интеграция (замена
   installroot/nbd-путей на guestmount+userns, снос sudoers, doctor-
   предусловия) — следующий этап; вместе с ней e2e 07 переписывается
   (nbd-верификация → guestmount) и получает позитивный online-путь
   (загружаемый гость с QGA), потому что дефолтный smart-путь не покрыт
   e2e-позитивом (только юниты с mock + негатив).
6. **doctor после онлайн-пути**: [DONE] helper/sudoers — не «нужно для
   работы», а «понадобится, только если VM не загрузится»: обе проверки
   (andler-helper presence и passwordless sudo) понижены с fail до warn,
   fix-текст объясняет, что нужны только для offline rescue (qemu-nbd/
   chroot), а умный онлайн-путь не требует root на хосте. Комментарий про
   «translator file ops» поправлен ранее.
7. **UX-паттерн**: `andler guest install <pkg>` сам выбирает путь (онлайн →
   автозапуск → chroot), не три отдельные команды; `--offline` — явный
   обход. Как `andler connect` (auto + `--level`).

### Phase-exit — чек-лист сверх обычного гейта

Обычный гейт (build/test/clippy/fmt, §Pre-Merge Verification из AGENTS.md)
проходит каждый коммит на ветке фазы — это не новость, так работает весь
репозиторий. Перед тем, как смёржить ветку фазы в `main` (fast-forward или
rebase, см. AGENTS.md — не squash), дополнительно:

1. Полный e2e-сьют зелёный (не только unit + round-trip, которые гоняются
   на каждом коммите).
2. Guardrails этой фазы из §13 перепроверены явно — не «наверное ничего не
   сломали», а по списку: какие пункты §13 relevant для этой фазы, для
   каждого — как проверено (тест, e2e, ручная проверка с указанием команды).
3. Статус фазы в таблице «Порядок работ» (ниже) обновлён в мёрж-коммите.
4. Если фаза добавила постоянное соглашение (не разовый факт, а правило на
   будущее — например, паттерн владения состоянием супервизором из §2.4
   после того, как он реализован) — соответствующий раздел `AGENTS.md`
   обновлён в том же мёрже, по правилу «код и доки в одном коммите» из
   `AGENTS.md`, Documentation Sync. Этот план описывает то, что ещё в
   работе; `AGENTS.md`/`docs/ARCHITECTURE.md` — то, что уже стало фактом.
   Этот файл ни разу не цитируется по имени ни из кода, ни из другого
   дока, ни из `AGENTS.md` (см. Ревизию 4) — только по номеру/слагу фазы.
5. Если фаза целиком закрывает пункт(ы) `docs/ROADMAP.md` — статус там
   обновлён; если фаза целиком реализована и смёржена — соответствующий
   раздел этого документа сокращается до одной строки-указателя на
   итоговую доку, а не остаётся висеть как черновик рядом с уже принятым
   решением (иначе через 8 фаз этот документ станет источником путаницы, а
   не истины).
6. **Последняя фаза — дополнительно**: весь план удаляется из репозитория
   одним коммитом (не «опустошается» — удаляется файлом), и `grep -ri` по
   всему репозиторию (код, доки, `AGENTS.md`) подтверждает ноль оставшихся
   ссылок на его имя перед мёржем.

### Что не меняется в процессе рефакторинга

Ежедневная (не относящаяся к фазам плана) работа — багфиксы, мелкие фичи,
правки документации — продолжает коммититься прямо в `main`, как и раньше;
ветки — только для многокоммитных фаз этого плана. Если во время фазы
находится не относящийся к ней баг — это отдельный коммит в `main` (или в
свою короткую ветку), не примешивается в ветку фазы: guardrail-проверка
фазы должна проверять только то, что фаза реально меняет.

## Порядок работ

Дальше — две колонки зависимостей: **«жёсткая»** (без этого фаза физически
не может начаться) и **«поток»** (порядок для одного разработчика/одной
последовательной ветки работы; при двух параллельных потоках — не блокирует).
Ревизия 2 явно разводит эти два вида, потому что в первом черновике всё было
одной цепочкой 0→1→…→8, хотя часть работы (DiskChain, §B) технически не
требовала этого порядка.
