# ANDLER Guest-image — План архитектуры

> **Статус:** первый каркас плана (набросок). Опирается на решения, уже зафиксированные в `MASTER_PLAN.md` (§4) и `CORE_ARCHITECTURE_PLAN.md` (§4.4 — как демон использует готовый образ). Детали сборки и provisioning будут уточняться по мере приближения к реализации (см. порядок в core-плане, шаг 11).
>
> **ANDLER** = *Android Linux Emulator & Runtime*.

---

## 1. Обзор

Гостевой образ — минимальный Linux-образ с Android-слоем (Waydroid, Уровень A), собираемый и версионируемый в CI, а не на машине пользователя. Демон (`andlerd`) скачивает готовый артефакт по требованию при первом создании Android-инстанса и использует его как read-only `backing_file` для overlay-дисков конкретных инстансов (см. `CORE_ARCHITECTURE_PLAN.md`, §4.4).

Ключевое разделение ответственности: **guest-image отвечает за то, что внутри образа**, **core отвечает за то, как образ запускается и клонируется**. Этот документ — про первое.

---

## 2. Технологии

(набросок, требует уточнения перед реализацией)

- **Базовая Linux-система внутри образа** — минимальный дистрибутив с поддержкой Wayland-композитора, достаточный для запуска Waydroid (вероятные кандидаты: Alpine, Debian minbase, либо специализированный Arch-based минимальный rootfs — финальный выбор не зафиксирован).
- **Инструмент сборки образа** — не Rust-специфичный, отдельный shell/Makefile-пайплайн поверх существующих инструментов сборки образов уровня ОС (например `mkosi`, `debootstrap`-подобные инструменты или Alpine `mkimage`); выбор конкретного инструмента — открытый вопрос (см. §7).
- **Android-слой** — Waydroid, разворачиваемый и настраиваемый **во время сборки образа в CI**, а не скриптом `waydroid script` на машине пользователя при первом запуске (это и есть отличие "уровня A, готового из коробки" от ручной установки).
- **Транслятор архитектур (ARM → x86)** — `libndk`/`libhoudini`, встраиваются в образ на этапе сборки как опциональный provisioning-шаг, управляемый флагом сборки (соответствует полям `AndroidProfile.libndk` из core-плана, §4.4.1).
- **Сетевой provisioning** — `nftables`-правила внутри образа, настроенные заранее, без интерактивной настройки сети при первом запуске гостя.
- **Формат итогового артефакта** — `.qcow2` (совместим с `andler-disk`/`andler-qemu` напрямую, без конвертации на стороне демона).
- **Подпись и проверка целостности** — артефакт подписывается в CI (минимально — checksum, в перспективе — криптографическая подпись), демон обязан проверить перед использованием как `backing_file` (см. core-план §4.4.2, шаг 3).

## 3. Структура

(набросок, требует уточнения перед реализацией)

```
guest-image/
├── build/                     # пайплайн сборки образа
│   ├── base/                  # сборка минимального Linux-rootfs
│   ├── waydroid-provision/    # установка и настройка Waydroid внутри chroot/контейнера сборки
│   ├── translators/           # опциональная установка libndk/libhoudini
│   └── network/               # nftables-конфигурация, встраиваемая в образ
├── variants/                  # матрица вариантов сборки
│   └── (android_version) x (gapps/microg) x (libndk on/off) → отдельный артефакт
├── manifests/                 # метаданные версий образов (версия, checksum, дата сборки, размер)
└── ci/                        # CI-джобы для сборки и публикации артефактов
```

Каждая комбинация полей `AndroidProfile` (версия Android, gapps/microg, наличие транслятора) — это **отдельный собранный артефакт**, а не один образ с runtime-переключателями: это проще для воспроизводимости сборки, но увеличивает матрицу CI-джобов и общий объём публикуемых артефактов (см. открытые вопросы, §7).

## 4. Сборка

(набросок, требует уточнения перед реализацией)

### 4.1 Общий пайплайн (CI)

1. Сборка минимального Linux-rootfs выбранным инструментом (§2).
2. Provisioning Waydroid внутри собранного rootfs (без выхода в сеть пользователя — всё разворачивается в момент сборки в CI).
3. Опциональный provisioning транслятора архитектур согласно варианту матрицы сборки.
4. Применение сетевого provisioning (nftables).
5. Конвертация результата в `.qcow2`, генерация checksum/подписи.
6. Публикация артефакта вместе с манифестом версии (manifest содержит: версию Android, флаги варианта, checksum, размер, дату сборки — формат манифеста должен совпадать с тем, что ожидает резолвер в `andler-core`, см. core-план §4.4.4).

### 4.2 Версионирование артефактов

Каждый артефакт версионируется независимо от core/frontend (образ может обновляться без релиза core). Демон при резолве `AndroidProfile` (core-план §4.4.2) должен уметь сверяться с манифестом доступных версий и решать, использовать ли локально закэшированный образ или скачать более новый — политика обновления (всегда последняя версия / закреплённая версия на инстанс) — открытый вопрос (§7).

### 4.3 Канал доставки артефактов

Не зафиксирован. Кандидаты: GitHub Releases (просто, но лимиты на размер/трафик), собственный CDN/объектное хранилище (надёжнее для больших файлов, требует инфраструктуры), торрент/IPFS-подобная раздача (снижает нагрузку на канал, но сложнее для пользователя). Решение — открытый вопрос, не блокирует начальную работу над core (core ожидает только валидный путь к `.qcow2`, см. core-план §4.4.5).

## 5. Тестирование

(набросок, требует уточнения перед реализацией)

- **Сборка образа в CI** — проверка, что пайплайн воспроизводимо собирает артефакт без ошибок для каждого варианта матрицы.
- **Smoke-тест образа** — автоматический запуск собранного образа в CI под QEMU (тот же набор устройств, что в `CORE_ARCHITECTURE_PLAN.md` §2.4) и проверка, что Waydroid внутри успешно стартует и сообщает готовность (например, через serial-порт или фиксированный маркер в логе загрузки).
- **Проверка checksum/подписи** — тест на стороне core (`andler-disk`/`andler-core`), что демон корректно отказывается использовать образ с несовпадающей подписью.
- **Деградация при отсутствии сети** — проверка, что core даёт понятную ошибку, если базовый образ не закэширован и сеть недоступна, а не падает с низкоуровневой ошибкой файловой системы.

## 7. Открытые вопросы

- Финальный выбор инструмента сборки минимального rootfs (`mkosi` / `debootstrap`-подобное / Alpine `mkimage`).
- Канал доставки артефактов конечным пользователям (GitHub Releases / собственный CDN / иное) — см. §4.3.
- Политика обновления образов на стороне демона: всегда тянуть последнюю версию варианта или закреплять версию за уже созданным инстансом (важно, чтобы обновление базового образа не "сломало" существующие overlay-диски).
- Размер и количество вариантов матрицы сборки (§3) — версии Android × gapps/microg × наличие транслятора — может потребоваться сократить матрицу для старта, собирая не все комбинации сразу.
- Уровень B (свой android-runner вместо Waydroid) — зафиксирован в core-плане как поздний этап (см. `MASTER_PLAN.md`, §8, пункт 8), здесь не проработан.
