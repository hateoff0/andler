# ANDLER Presets — План архитектуры

> **Статус:** первый каркас плана (набросок). Опирается на решения, уже зафиксированные в `MASTER_PLAN.md` (§5) и `CORE_ARCHITECTURE_PLAN.md` (§4.4.3 — точка интеграции пресета с резолвом `InstanceConfig`).
>
> **ANDLER** = *Android Linux Emulator & Runtime*.

---

## 1. Обзор

Пресеты (рабочее название в продуктовой концепции — **ANDLER-Proton**) — структурированные данные (TOML/JSON) под конкретную игру/приложение: маппинг клавиш, рекомендуемый render backend, флаги транслятора архитектур, опциональные твики совместимости. Пресет — это **данные, не код**: применяется существующей логикой `andler-core`, а не отдельным сервисом или плагином с произвольным исполняемым кодом.

Ключевое ограничение архитектуры: пресет **не заменяет** механизм создания инстанса (резолв `AndroidProfile` → `InstanceConfig`, см. core-план §4.4), а применяется **после** него как частичный, явно ограниченный по полям оверрайд.

---

## 2. Формат данных

(набросок, требует уточнения перед реализацией)

- **Формат файла** — TOML (соответствует продуктовой концепции и MASTER_PLAN §5); JSON как альтернатива не приоритетна, но не исключена для каталога сообщества (см. §5).
- **Расположение** — `presets/<game-id>.toml` в монорепозитории на старте; позже — отдельный каталог сообщества вне монорепо (см. §5).
- **Примерная структура одного пресета (черновик, не финальная схема):**

```toml
[meta]
id = "example-game-id"
display_name = "Example Game"
android_version_recommended = "13"

[render]
backend = "venus"          # соответствует RenderBackend из core-плана §4.1
fps_limit = 60

[resources]
cpu_cores_min = 4
ram_gb_min = 8

[translator]
required = true            # требует libndk/libhoudini — см. guest-image §2

[keymap]
# формат маппинга клавиш на тапы/свайпы — не зафиксирован,
# зависит от реализации keymapping-редактора во frontend (см. PRODUCT_CONCEPT.md §10)
```

Поля `[keymap]` зависят от формата, который выберет frontend-редактор маппинга (см. `FRONTEND_PLAN.md`) — на этом этапе зафиксировать их рано, схема будет дозревать вместе с UI keymapping-редактора.

## 3. Валидация

(набросок, требует уточнения перед реализацией)

- **JSON Schema** как формальное описание допустимой структуры пресета (упомянуто в продуктовой концепции и MASTER_PLAN §5) — конкретная схема пишется параллельно с финализацией формата данных (§2).
- Валидация происходит **на стороне `andler-core`** при применении пресета, а не во frontend — UI может делать предварительную (UX) проверку, но источник истины — core, как и для остальной конфигурации.
- Невалидный или частично невалидный пресет не должен приводить к падению/панике демона: ожидаемое поведение — явная ошибка с указанием, какое поле не прошло валидацию, без частичного применения остальных полей.

---

## 4. Применение пресетов

(набросок, требует уточнения перед реализацией)

Применение пресета — это шаг **после** `AndroidProfile::resolve()` (core-план, §4.4.3): пресет получает на вход уже собранный `InstanceConfig` и применяет оверрайд по ограниченному, явно перечисленному набору полей (render backend, fps_limit, рекомендации по CPU/RAM, флаг транслятора, keymap-метаданные). Пресет **не может** переопределять поля, не относящиеся к его зоне ответственности (например, сетевые настройки или путь к диску) — список разрешённых для оверрайда полей фиксируется в реализации, а не оставляется открытым.

- Применение пресета частично (выбрать только часть полей пресета) — упомянуто как возможность в MASTER_PLAN §5, конкретный UX/API для частичного применения не проработан (см. §6).
- При конфликте пресета и пользовательской ручной настройки конкретного инстанса — приоритет за явным пользовательским значением, пресет применяется только к ещё не заданным/значениям по умолчанию (соответствует продуктовому принципу "разумные настройки по умолчанию + полный доступ под капотом", см. `PRODUCT_CONCEPT.md` §3).

## 5. Каталог сообщества

(набросок, требует уточнения перед реализацией; вне скоупа первой реализации — см. MASTER_PLAN §8, пункт 7)

- На старте — несколько примеров пресетов прямо в монорепозитории (`presets/` согласно структуре MASTER_PLAN §2).
- В перспективе — отдельный репозиторий/веб-каталог для публикации пресетов сообществом (упомянуто в продуктовой концепции и MASTER_PLAN §5 как "вне скоупа этого плана").
- Открытый вопрос: механизм доверия к пресетам сообщества — пресет может рекомендовать настройки рендеринга/транслятора, но не должен превращаться в вектор для произвольного исполняемого контента; раз пресет — чистые данные (TOML/JSON), а не скрипты, риск ограничен, но валидация (§3) должна быть строгой и публичной (например, CI-проверка каждого PR в каталог сообщества против JSON Schema перед публикацией).

## 7. Открытые вопросы

- Точная схема `[keymap]` — зависит от формата keymapping-редактора во frontend, не может быть зафиксирована раньше него.
- UX и API частичного применения пресета (выбрать только часть полей, а не весь пресет целиком).
- Механизм доверия/модерации для каталога сообщества (§5) — когда каталог появится за пределами монорепозитория.
- Разграничение ответственности пресета и встроенного маппера ввода при конфликте настроек одного приложения — отмечено как открытый вопрос ещё на уровне продуктовой концепции (`PRODUCT_CONCEPT.md`, §28), здесь не решено.
