# ANDLER Frontend — План архитектуры GUI-клиента

> **Статус:** архитектурный план frontend-части. Описывает выбор технологий, структуру, взаимодействие с core, видео-рендеринг и упаковку.
>
> **ANDLER** = *Android Linux Emulator & Runtime*.
> **Язык:** Rust (Tauri) + TypeScript (React/Svelte)

---

## 1. Требования и цели

### 1.1 Ключевые требования
- Общение с `andlerd` по тому же gRPC API, что и CLI (никакой отдельной протокольной логики)
- Отображение **живых миниатюр экрана инстансов** — встроенный видео-рендеринг (VNC/SPICE/scrcpy-подобный поток)
- Нативное десктоп-приложение для Linux (трей, глобальные горячие клавиши, drag-and-drop, интеграция с уведомлениями)
- Возможность частичного переиспользования интерфейсного кода с future companion-app (мобильное приложение)
- Популярный и хорошо документированный стек для open-source контрибьюторов

### 1.2 Архитектурные принципы
- Frontend — строго тонкий клиент над gRPC API core
- Никакой собственной логики виртуализации/дисков/сети
- Единый источник истины — демон `andlerd`

## 2. Выбор технологий

### 2.1 Сравнение вариантов

| Вариант | Язык UI | Плюсы | Минусы |
|---|---|---|---|
| **Tauri + веб-фронтенд** | TypeScript/HTML/CSS, нативная обвязка на Rust | Нативная обвязка на Rust — общие типы/крейты можно шарить; маленький бинарь и низкое потребление памяти; огромная экосистема веб-компонентов; проще найти контрибьюторов | Webview на Linux — WebKitGTK, есть нюансы с GPU-композитингом видео-потоков |
| **egui (чистый Rust)** | Rust | Всё на одном языке с core, минимальные зависимости, отличная производительность для прямого рендеринга | Меньше готовых "красивых" виджетов, дизайн требует больше ручной работы |
| **GTK4 + libadwaita** | Rust (биндинги к GTK) | Максимально нативный вид и интеграция с GNOME, привычно пользователям Linux | Биндинги к GTK на Rust менее эргономичны; меньше "вау"-дизайна без усилий |
| **Qt (cxx-qt или QML)** | C++/QML, мост к Rust | Очень мощный для сложных десктоп-приложений с богатым UI и встроенной поддержкой видео | Внесение C++/QML в проект на Rust увеличивает порог входа для контрибьюторов |
| **Electron + веб-стек** | TypeScript/HTML/CSS | Самый широкий пул контрибьюторов, проще всего стартовать | Тяжёлый (свой Chromium в каждом инстансе), высокое потребление RAM — не рекомендуется |

### 2.2 Рекомендация: Tauri + веб-фронтенд

**Обоснование:**
- Нативная часть Tauri пишется на Rust — переиспользуем типы из `andler-core`/`andler-rpc` напрямую
- Малый размер и память (в отличие от Electron) — соответствует принципу прозрачного, экономного потребления ресурсов
- Видео-миниатюры и live-стрим экрана инстанса реализуются как `<video>`/`<canvas>` элемент, получающий кадры через локальный WebSocket/gRPC-стрим
- Самый широкий пул потенциальных контрибьюторов (веб-стек плюс немного Rust в обвязке)

**Запасной план:** Если WebKitGTK даст проблемы с плавностью видеопотоков — **egui**, так как того же языка, что и core, и не имеет проблем с встраиванием произвольного видео/GPU-рендеринга (через `wgpu`)

## 4. Архитектура взаимодействия

### 4.1 Связь frontend ↔ core
Frontend **никогда** не реализует свою логику виртуализации/дисков/сети — он строго тонкий клиент над тем же gRPC API (`andler-rpc`), которым пользуется CLI.

### 4.2 Потоки данных
1. **gRPC-стриминг** для метрик и логов инстансов
2. **WebSocket** для видеопотока экрана инстанса (через Tauri-бэкенд)
3. **Tauri commands** для синхронных операций (start/stop/pause/create)

### 4.3 Типы данных
- Переиспользование сериализуемых типов из `andler-core`/`andler-rpc`
- Общая схема конфигурации между CLI и GUI

## 5. Видео-рендеринг экрана инстанса

### 5.1 Архитектура
```
┌─────────────────────────────────────────────────────────────────┐
│                    InstanceLiveView Component                  │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │              <video> / <canvas> element                    ││
│  │              (получает кадры через WebSocket)               ││
│  └─────────────────────────────────────────────────────────────┘│
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│                    Tauri Backend (Rust)                         │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │  WebSocket server → QEMU VNC/SPICE stream                 ││
│  └─────────────────────────────────────────────────────────────┘│
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│                        andlerd (демон)                          │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │  QEMU VNC/SPICE server (через QMP)                        ││
│  └─────────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 Реализация
- Tauri-бэкенд открывает VNC/SPICE соединение с QEMU
- Стриминг кадров через WebSocket в веб-часть
- `<video>` элемент для отображения потока
- Обработка ошибок и переподключение

## 6. Компоненты интерфейса

### 6.1 InstanceList
- Список всех инстансов с миниатюрами экрана
- Статус, метрики ресурсов, быстрые действия
- Drag-and-drop файлов для загрузки в инстансы

### 6.2 InstanceCreateWizard
- Пошаговый мастер создания инстанса
- Выбор backend (qemu/rust-vmm/auto)
- Настройка CPU, RAM, disk, network, render backend
- Валидация конфигурации

### 6.3 InstanceLiveView
- Видео-миниатюра/живой экран инстанса
- Управление окном (размер, fullscreen)
- Горячие клавиши, глобальные хоткеи

### 6.4 ResourceMonitor
- Мониторинг CPU/RAM инстансов в реальном времени
- Графики метрик (через gRPC streaming)
- Настройки ballooning/zram

### 6.5 Settings
- Глобальные настройки приложения
- Управление backend'ами (qemu/rust-vmm)
- Настройки сети, дисков, обновлений

## 7. Связь с другими частями проекта

### 7.1 Core (обязательная)
- Общий gRPC API через `andler-rpc`
- Переиспользование типов и конфигураций
- Единый источник правды для состояния инстансов

### 7.2 Guest-image (опционально)
- Загрузка образов из каталога
- Валидация образов перед использованием
- Показ доступных образов в UI

### 7.3 ANDLER Presets (опционально)
- Применение пресетов к инстансам
- Выбор пресетов в UI
- Валидация пресетов через JSON Schema

## 8. Упаковка и дистрибуция

### 8.1 Tauri-бинарь
- Нативная обвязка через Tauri
- Минимальный размер и потребление памяти
- Интеграция с системным треем и уведомлениями

### 8.2 Зависимости
- **Системные:** QEMU (qemu-system-x86_64, qemu-utils)
- **Runtime:** WebKitGTK (через Tauri)
- **Не встраиваются:** QEMU, образы, пресеты

### 8.3 Форматы дистрибуции
- **AppImage:** GUI (+ опционально core для портативного запуска)
- **.deb:** GUI (зависит от andler-core)
- **.rpm:** GUI (зависит от andler-core)
- **Flatpak:** только GUI (требует отдельного решения по доступу к KVM)

## 10. Порядок реализации

1. **Tauri-бэкенд** — базовая обвязка, RPC-клиент, первые commands
2. **Веб-часть** — базовые компоненты, API-слой, стили
3. **InstanceList** — список инстансов, статусы, метрики
4. **InstanceCreateWizard** — мастер создания, валидация
5. **InstanceLiveView** — видео-стриминг, миниатюры экрана
6. **ResourceMonitor** — графики, мониторинг в реальном времени
7. **Settings** — глобальные настройки, управление backend'ами
8. **Интеграция с core** — полный цикл работы с инстансами
9. **Упаковка** — AppImage, .deb, .rpm
10. **Тестирование** — юнит, интеграционные, E2E

## 11. Открытые вопросы

- **Tauri vs egui** — финальное решение нужно подтвердить прототипом видеопотока в WebKitGTK
- **React vs Svelte** — не принципиально для архитектуры, можно решить по предпочтениям контрибьюторов
- **Видео-стриминг** — нужно проверить плавность на реальных GPU и видеокартах
- **Системные интеграции** — тре, горячие клавиши, уведомления требуют тестирования на разных DE
